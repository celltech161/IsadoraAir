# r0128: Verified Audio-Equivalent Duplicate Resolution

r0128 extends r0127's explicit Library duplicate-resolution workflow to a second kind of conclusive
evidence. Authorized **Manage tracks** operators may ask a new reconciliation scan to verify a
bounded number of likely two-Track pairs. When both files are safely decoded and their complete
canonical PCM identities are equal, the existing preview, confirmation and guarded deletion
workflow can resolve the pair.

Nothing is matched, selected or deleted automatically. Audio verification is **Off** by default and
is available only as an operator choice for up to 25, 50 or 100 likely pairs in one scan.

## Three different findings

The page and report deliberately distinguish:

1. **Identical source-file bytes.** This is the existing r0127 `exact` finding. Both complete files
   had the same SHA-256 and full scan-time file witnesses.
2. **Verified identical decoded audio.** New in r0128, an `audio_equivalent` pair records both full
   decoded-audio identities and their file witnesses. Both files decode to the same complete audio
   with the same running FFmpeg version, or trusted current-version waveform-cache evidence proves
   the same identity.
3. **Similar metadata without proven audio equality.** Matching title, artist, duration or ISRC is
   only a likely or uncertain finding. It remains review-only and cannot authorize deletion.

Groups containing three or more Tracks are not resolvable through this workflow. The feature is not
perceptual similarity matching and does not infer equality from tags, names or duration.

## Bounded, descriptor-bound verification

Verification runs only in the existing asynchronous reconciliation command, never in a web request.
The browser sends one fixed choice: Off, 25, 50 or 100 pairs. The scanner enforces independent pair
and decode limits, decodes a file at most once per scan, allows at most two decodes per requested
pair, gives one file at most five minutes and caps all audio verification at 30 minutes.

FFprobe and FFmpeg read the already-open regular file through `/proc/self/fd/N`; they do not reopen a
Library pathname. The scanner compares the opened descriptor with the walked file witness before
and after decoding. The Linux `/proc` filesystem must therefore be mounted and usable by the
reconciliation process. Both subprocesses share one monotonic per-file deadline, and every file also
shares the aggregate deadline.

Trusted waveform-cache identities may avoid a decode. Cache evidence from a different FFmpeg
version is never used to prove a mismatch: the affected file is decoded again with the running
version if the pair, decode and time budgets permit. Incomplete, failed, timed-out or cross-version
evidence remains non-deletable.

## Existing r0127 safeguards remain authoritative

The new evidence feeds the existing r0127 workflow. Preview remains read-only. Apply still requires
a fresh, operator-bound, short-lived, single-use token, observes and revalidates both Track rows,
files, evidence, categories, database references and live playout, and commits at most one pair in a
transaction. Uncertain HTTP outcomes stop the browser sequence without retrying.

The evidence kinds are not interchangeable: an exact-byte finding must carry its complete byte-hash
evidence, and a decoded-audio finding must carry complete current audio-verification evidence for
both files. An old report, a label by itself, metadata similarity or a partial identity cannot
authorize deletion.

Choosing a survivor does not merge or replace Track-specific information. Metadata, the primary
category, readiness, historical plays, cue markers, waveform state, requests, logs and other Track
attributes remain attached to their existing rows. As in r0127, additional categories may be
explicitly selected during preview, and VoiceTrack deletion requires its separate acknowledgment.

## Report transition

Existing reports remain readable. They cannot gain new deletion authority merely because r0128 is
installed. To produce usable evidence for remaining likely pairs, an operator must deliberately run
a **fresh reconciliation scan with audio verification enabled**. The page explains why a pair was
verified, differed, was skipped or exhausted a bound.

Run verification only in an approved operational window: it performs bounded media reads and audio
decoding. Publication and installation do not start a scan.

## Deployment declaration

* **Migration:** none; no migration-authorization companion exists or is required.
* **Python requirements and APT packages:** unchanged; FFmpeg, FFprobe and Linux `/proc` are existing
  station prerequisites, not new packages in this release.
* **Systemd and protected runtime:** no unit, timer, policy, descriptor, attestation or protected
  generation change. `protected_runtime` is `null`, so no offline release signature is created.
* **Static and nginx:** unchanged; no `collectstatic` action.
* **Restart:** `isadoraair-gunicorn` only, so Gunicorn loads the changed application code and page
  template.
* **Not restarted:** engine, encoders, Monitoring, RBDS, Active Messages, reconciliation processes,
  spoken rendering and every other station service.

Publishing r0128 does not authorize installing it at KOGR or WRJE, running a production
reconciliation scan, decoding station media, resolving a pair or deleting a Track. See
[r0128_installation.md](r0128_installation.md).

## Not in this release

* no perceptual or approximate audio matching;
* no automatic resolution, unattended deletion or metadata merge;
* no resolution of groups with three or more Tracks;
* no scanner daemon, service, timer or protected-runtime change;
* no migration, scheduler, engine, encoder or playout change;
* no Hour Refill or native Active Messages activation.
