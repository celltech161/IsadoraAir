# r0149: Hour Refill Start Next eligibility with a connected Remote DJ (roadmap 2.27)

r0149 contains one Hour Deficit Refill eligibility correction (roadmap 2.27) with its revised field-qualification
contracts, and nothing else. Restart **Gunicorn and the audio engine**. **The engine restart interrupts program audio**
and is subject to the r0144 engine restart safeguard.

**r0149 does not activate Hour Refill.** It changes no policy value, switch or station setting, and it arms no host. A
station keeps whatever Hour Refill policy it has: Off, or **Observation only (dry run)**.

## What changes for the operator

**The inherited problem.** A Start Next was never recorded as an Hour Refill cause while any Remote DJ was
**connected**, even one that was only monitoring with the microphone Off.

**The correction.**

- **A connected Remote DJ who is only monitoring no longer excludes an otherwise eligible Start Next** from Hour
  Deficit Refill. The connection is still recorded as evidence.
- **Studio Console and Remote DJ workspace Start Next commands keep the same permission checks.** r0149 changes
  nothing about who may press Start Next or what Start Next does on air.
- **Actual Manual mode remains excluded.**
- **Actual local or remote microphone engagement remains excluded:** a live studio microphone or an open Remote DJ
  gate.
- **A requested Remote DJ microphone remains excluded even while temporarily muted**, as can happen during reconnect
  recovery, when the engine keeps the Remote DJ's On intent but holds the gate muted.
- **Emergency Mute cancels microphone intent.** It is not a "muted but still requested" case: afterwards that session
  counts as mic Off unless another microphone is live, and an On press is refused while the emergency latch is set.
- **Unknown microphone state fails closed:** it counts as engaged, and the Start Next is excluded.
- **The connection-only exception applies only to a nonempty set of qualified causes that are all Start Next.** It
  does not apply to an empty set, to any other cause type, or to a mixed set. A mixed set is never trimmed to its
  Start Next causes to escape the block.
- **The existing restrictions for request substitution, Eject, automatic skip and media failure are intact**: a
  connected Remote DJ still blocks every set that contains one of them.

The **Capture start next** help text on the Hour Refill Policy page in Django Admin now describes this rule. That is
the only user-interface change.

## Eligibility is not a guarantee

An eligible Start Next **does not guarantee a proposal, and does not guarantee an installation**. Every existing gate
still applies:

- the net-shortage threshold on the whole hour (a Start Next-only set needs a net shortage of **more than 30 s**;
  stricter thresholds for other cause types and mixed sets are unchanged, and exactly 30.000 s or 60.000 s does not
  qualify);
- the fitter, with at most two music tracks and no modelled overrun;
- the safety reserve;
- the 20 s minimum insertion lead;
- protected closing material;
- media readiness;
- category, recency, separation, request and dedication-adjacency rules;
- the guarded install transaction (fresh snapshot, compare-and-swap, locked rows, policy re-read);
- engine adoption checks.

**Safety reserve.** The implemented formula is unchanged: **5 s plus 1 s per inserted item**. One inserted track:
**6 s**. Two inserted tracks: **7 s**. Two tracks plus one PSA: **8 s**. (An earlier wording in one contract document
stated 7, 8 and 9 s; the code and tests were always 6, 7 and 8 s.)

## Revised field qualification

The five roadmap documents record the accepted contracts. The rollout packet
(`docs/roadmap/2_27_PHASE_D_ROLLOUT_PACKET.md`) now requires:

- an initial **14-day** shadow observation;
- **cause-specific** supervised pilot qualification: field evidence for the cause type proposed for activation;
- **no fixed 30-cause or ten-proposal prerequisite** (both are withdrawn);
- a review of **all available unique relevant proposals**;
- isolated partial-hour regression qualification where the station schedules no partial-hour takeover;
- a **separate operational qualification** before a station deliberately relies on partial-hour scheduling;
- the corrected projection timing methodology;
- dead air and waiting intervals **reported separately**, never as projection error;
- **separate authorization** for host arming and for installation (clearing Observation only);
- **seven days** of limited-install observation;
- **at least one actual refill successfully observed airing** before operational acceptance.

The original observation clock **does not restart** because r0149 is installed. Because r0149 changes which Start
Next events are eligible, a focused post-installation verification of the newly permitted path is required before any
live pilot (`r0149_installation.md`).

## Timing evidence and its limits

- The simple source-position-zero formulas apply **only to eligible fresh-start segments**.
- Continuation segments (seek, resume, restart recovery) are **excluded by default**, unless the engine journal
  supplies a sufficiently authoritative starting position.
- The November 11 projection result of **−0.410 s is a reconstructed estimate**, using the marker evidence
  available. It is not an observed successor event.
- The **175.210 s dead-air interval** in that hour is independently supported. It is a continuity finding, not
  projection error.
- The **two available measurable Start Next cause-hours are supporting evidence, not statistical proof**.
- The targets are unchanged: projection error at the 95th percentile **≤ 3 s** and a maximum of **≤ 5 s**.

r0149 adds no runtime timing field and changes no projection arithmetic.

## Limitations of the change (accepted)

1. A requested Remote DJ microphone is judged from the engine's desired-On intent for the current session; r0149
   adds no new operator signal or counter for excluded Start Next events.
2. Exclusion reasons are still not counted or shown in Admin: a Start Next that records no cause leaves no cause row.
3. Capture is best effort, as before: it never blocks the Start Next it observes.
4. Hour Refill remains default-Off. Nothing here is field-accepted for live installation at either station.

## Unchanged behavior

Playout, Start Next audio, the first-real-audio recovery of r0147, the deck mixer and deck bus of r0146, engine
startup, shutdown and resume, Remote DJ connection and reconnection, ducking, Manual hold, the microphone gate, request
substitution, Eject, automatic skip, media failure, live fill and the guarded installer are unchanged. In
`engine.py`, only the Start Next ownership snapshot changes and one read-only microphone helper is added.

## Operational impact

There is no migration: `migrations_required` is empty, `migration_compatibility` is `null` and no manual migration
authorization exists. There are no new packages, Python requirements, static assets, collectstatic, nginx changes,
systemd units, manual bootstrap, station configuration, Hour Refill policy-data or protected-runtime changes, no
GStreamer upgrade, and `protected_runtime` is `null`. Restart exactly: 1. `isadoraair-gunicorn` 2. `isadoraair-engine`

The engine runs the corrected capture and projection; Gunicorn loads the revised Admin help text and the changed
refill modules. The encoders and Liquidsoap, Monitoring, RBDS and the persistent workers keep running. The engine
restart **interrupts program audio** briefly; it is not a Gunicorn-only, non-disruptive release. Install in an
approved maintenance window. A station on r0144 or later installs from an Update Center with the **engine restart
safeguard**, which refuses the installation while a studio microphone is live, a Remote DJ is connected (even with its
microphone Off) or engine status is unknown. r0149 does not change that safeguard; do not override it to install. A
station on an earlier release still receives every intervening migration and restart in its cumulative plan.

Publication does not authorize installation, and installation does not authorize Hour Refill activation: each station
requires separate preflight, installation authorization and operational acceptance, and separate activation
authorization; see `r0149_installation.md`.
