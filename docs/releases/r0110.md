Predecessor: **r0109** (`6694b15672f520815b73e2b0e054639f9263d2ba`).
Protected runtime: **unchanged — generation 13** (runtime version 11, manifest
protocol 5); `"protected_runtime": null`, no new descriptor, attestation or
signing.
Accepted engineering baseline: `68676f622e201044d12b326c08a99edec2322543`
(Phase D1 → D2A → D2B → D3A → D3B), plus the release commit on
`release/r0110-phase-d-active-messages` and its metadata-only migration
authorization companion (`deploy/migration_authorizations/r0110.json`).

> **Legacy OGRemote remains authoritative. r0110 does not change what airs.**
> `NATIVE_AIRING_AVAILABLE = False` is a source-level constant: no native
> active message can air, whatever the database or an administrator does.

## Release notes

### New

- **Native urgent / public-address message authority** — active messages live
  in IsadoraAir's own database (`active_messages`): a strict lifecycle
  (prepared → active → cleared/expired) with an append-only history, the
  station policy (limits, cadence, stinger) and one exact aggregate per
  airing, rendered and verified by the existing isolated renderer.
- **Exact producer/content-type identity** — station-defined content types
  (`produced_content`): urgent, public address, regular and test, each with its
  own settings. A message belongs to one exact type; a producer may have one
  active message per type, so several public-address and urgent types can be
  active together, and a replacement supersedes only the same type.
- **Producer content assignments** — which users may produce which exact
  types (managed in Django Admin). An assignment narrows the existing
  `active_message.produce` capability; control works across all enabled types.
- **Self-publish vs operator review** — per type: an assigned producer may
  publish their own message, or (self-publish off) the saved draft waits for
  an operator to publish it. A draft is the review state; there is no second
  approval workflow.
- **Owner recall** — per type: a producer may recall their own active
  message when the type is recallable (no assignment needed to withdraw).
- **Producer "My Messages" page** — `/iportal/messages/`: the producer's
  types, their active message and every draft, with Publish, Recall and
  Discard (each on one exact message, confirmations for recall and discard).
- **Shared iPortal recorder for active messages** — record, import, edit and
  preview a message's audio in the same workstation evergreen voice tracking
  uses. Its subject is one exact message UUID; authorization is checked for
  that exact message before any upload, preview or save. **Save Audio is not
  Publish**: saving binds audio to the draft only. Two tabs editing one draft
  cannot overwrite each other (optimistic revision checked under the message
  row lock; the stale tab gets a conflict).
- **Shared recorder** — a subject-aware authorization hook for every
  consumer, and per-consumer wording; evergreen voice tracking is unchanged.

### Playout architecture (dormant in r0110)

When native airing is eventually enabled (Phase G), an active message airs
through the station's existing machinery only:

```
D2A aggregate (immutable, verified ProductionMedia)
→ immutable UrgentPA library Track (UrgentPA/am-<execution>.flac)
→ existing insert_urgent
→ ordinary LogItem
→ existing A/B decks
→ existing GStreamer/program chain
```

No playback lane, player, mixer, selector or sink was added. The engine
carries the accepted D2B hooks (exact insertion correlation, deck-open
authority, first-real-buffer/EOS evidence); they do nothing while airing is
unavailable. Weather and AMBER alerts are unchanged and keep priority.

### Dormant safety

- `active_messages.services.NATIVE_AIRING_AVAILABLE = False` (code). The
  policy's `native_airing_enabled` defaults to False, and enabling it is
  refused while the code gate is false; every publication, dispatch,
  admission and deck-open step requires both.
- **No active-message worker unit exists** — nothing renders, publishes or
  dispatches an aggregate.
- **Nothing native can air.** Publishing a message makes it ACTIVE in the
  domain only; no execution is materialized by the web workflow and no engine
  command is sent.
- **Legacy OGRemote remains authoritative**; its poller and processing are
  untouched. No OGRemote data is imported.
- Weather/AMBER, music, imaging, logs, voice tracking and spoken content
  behave as before.

### Not included

Regular OGRemote content replacement (D3C), the test-audio workflow, the
operator control board (D3D), monitoring, retention, the active-message
worker/service packaging (D3E), legacy data import, cutover (Phase G) and
legacy retirement (Phase H).

### Compatibility

- The `.env` needs **no edit**; no new setting, package, unit, nginx or
  protected-runtime change.
- Non-staff producers reach `/iportal/messages/` only if their group's
  GroupAccess allowlist includes `/iportal/` (staff bypass it). Nothing in
  this release grants it.

## Migrations

The first release containing Phase D migrations. From an r0109 schema the
target plan (confirmed with the r0110 code's own `updatecenter_probe` against
a database migrated by the exact r0109 code) is exactly, in order:

| # | Migration | Operations | Classification |
| --- | --- | --- | --- |
| 1 | `produced_content.0001_initial` | CreateModel ×2 | additive |
| 2 | `active_messages.0001_initial` | CreateModel ×4 | additive |
| 3 | `active_messages.0002_playout_correlation` | CreateModel ×2 | additive |
| 4 | `active_messages.0003_message_content_type` | 0 AddField (nullable), 1 RunPython | 0 additive, **1 manual** |
| 5 | `active_messages.0004_message_content_type_identity` | 0 AlterField, 1 RemoveConstraint, 2 AddConstraint | **manual** |
| 6 | `authz.0008_active_message_capabilities` | 0 RunPython | **manual** |

`migration_compatibility` is `additive`. The five manual operations are
covered by the trusted **migration-authorization companion**
`deploy/migration_authorizations/r0110.json`, added in a separate
metadata-only commit after the release commit and binding the release
commit, the manifest's SHA-256 and each migration file's exact SHA-256
(docs/UPDATE_CENTER.md, "Trusted companion migration authorization"). A
station whose plan contains exactly these operations needs no local approval;
any other plan falls back to exact station-local approval.

What they do:

- **`authz.0008`** — seeds `active_message.produce` and
  `active_message.control` and grants both to **Station Administrator only**;
  Contributor and Remote Host receive neither. Staff/superuser keep the
  existing authorization bypass.
- **`produced_content.0001`** — creates `ProducedContentType` and
  `ProducedContentTypeAssignment` (empty apart from the next item).
- **`active_messages.0001` / `0002`** — create the message, execution, event,
  policy, publication and insertion tables (empty; the policy row is created
  on first use, airing disabled).
- **`active_messages.0003`** — adds the message's content type (nullable),
  creates two native compatibility types if absent — `urgent_pa` (urgent) and
  `public_address` (public address) — both explicitly with
  `producer_self_publish=False` and `recallable=False` (the dormant D1
  authority: only control activates or clears), and backfills any existing
  message from its frozen kind. A fresh r0109 station has no messages.
- **`active_messages.0004`** — makes the content type required and changes
  the one-active-message rule from (producer, kind) to (producer, content
  type).

No OGRemote database rows, users, categories, assignments, files or
submissions are imported.

## What the update does

Planned by Update Center from r0109:

| Step | Action |

| 2 | Stage the exact r0110 release target |
| 3 | Target migration probe; validate the r0110 companion authorization (covers all five manual operations) |

| 6 | Re-probe: schema clean |
| 7 | Checkout fast-forward r0109 → r0110 |

| 9 | No unit install, no `daemon-reload` |
| 10 | Restart `isadoraair-gunicorn` (apps, settings, URLs, admin, views, recorder, producer UI) and `isadoraair-engine` (the accepted D2B engine hooks), in protected restart order |
| 11 | Postflight: exact checkout, clean schema, Gunicorn health |

**Not restarted, deliberately:**

- `isadoraair-render` — r0110 adds the aggregate `assemble` operation to the
  renderer (D2A), but nothing in a deployed r0110 requests an aggregate: there
  is no active-message worker unit and airing is closed. The renderer is not
  one of the five services a manifest may restart, and its unit file did not
  change, so r0110 neither declares an unsupported restart nor a false unit
  change. The running r0109 renderer keeps serving spoken content with the
  unchanged `render` protocol; when it next restarts it runs r0110 code, which
  is backward compatible and gains `assemble`. Phase D3E packages the worker
  and service readiness before cutover.
- `isadoraair-spoken-render-worker` — its r0109 path is unchanged and
  compatible; shared render-client changes concern only Phase-D rendering,
  which is dormant.
- `isadoraair-validation`, `isadoraair-monitoring`, `isadoraair-encoders`,
  `isadoraair-rbds` — nothing they run changed.

## Rollback boundary

- Update Center promises **no automatic rollback** (docs/UPDATE_CENTER.md,
  "Failure, retry, and rollback").
- **Before migrations** (steps 1–4): a failure leaves the live application
  unchanged.
- **After migrations, before the checkout** (steps 5–6): the additive Phase-D
  tables and capability rows stay, and r0109 code keeps running — it does not
  use the new apps (verified during packaging: r0109 `check` and
  `migrate --check` pass against the r0110 schema).
- **After the checkout**: failures are `failed`/`manual_intervention_required`
  with evidence; fix forward with a corrected release.
- **The schema is forward-only.** The checkpoint is a disaster-recovery
  reference for the pre-r0110 database, not a rollback tool.
- Even after a successful installation **no active-message content can reach
  air**: the code-level gate is false.
