## Included changes

### Remote PTT button: owner PTT and administrator Disable/Enable

The existing Remote PTT button now serves both roles. Its behaviour depends on
which browser owns the Remote DJ connection, never on the account name or
staff/superuser flags.

**Owning browser** (any account, superuser included):
- ordinary push-to-talk ON/OFF;
- while an administrator has disabled Remote PTT, the button reads **PTT
  DISABLED** and cannot open the microphone.

**An administrator observing another browser's session** (holding
`remote_dj.emergency_mute`):
- **Disable:** forces the microphone OFF and latches Remote PTT off. This works
  whether the microphone is LIVE or OFF.
- **Enable:** releases the latch only. **Enable never opens the microphone.**
  The DJ must press their own PTT again to transmit.

**Everyone else:** a read-only indicator.

**No Remote DJ connected:** the button keeps its local microphone calibration.

### Connect button: Connect, Disconnect and Kick

The existing two-line Connect button now also carries Kick:

| Situation | Button |
|---|---|
| No Remote DJ | Connect |
| This browser owns the session | Disconnect (own session only) |
| This browser has a leftover local link | Close stale link (local cleanup only, never a Kick) |
| Another browser's session, with `remote_dj.force_disconnect` | **Kick Remote DJ**, after a confirmation naming the DJ and session |
| Another browser's session, without the grant | Read-only "Remote in use" |

- An administrator's own connected browser always gets Disconnect, never Kick.
- Clicking Kick never starts a new connection.
- The page never starts a connection while another session is live.

### The dedicated emergency row is removed

The separate Emergency Mute, Release Emergency Mute and Kick Remote DJ buttons
are gone. Administrator progress and the engine-confirmed outcome appear on a
compact status line, on the full Console and only for capability holders.
HTTP 202 still means only "queued".

The `/remote-dj/` talent page gains no administrator behaviour.

### Engine-authoritative PTT generation (stale PTT-ON correction)

Each Remote DJ session carries an engine-owned PTT generation. It starts at 1
for every new session and advances when:
- an administrator Disables (once);
- an administrator Enables (once);
- a recovery episode begins (once);
- the first distinct authorization or protective forced-off occurs (once).

How activation is enforced:
- The owning browser binds each press to the generation it observed. A retry
  reuses the original request body and generation unchanged.
- The generation is part of the signed command proof.
- For PTT-ON, Django compares it with fresh engine status before queueing (HTTP 409
  `stale_generation`).
- For PTT-ON, the engine compares it again immediately before changing the gate
  (`stale_generation`).

So a PTT-ON pressed before Disable can never open the microphone after Enable.
Only a genuinely new, authorized press bound to the current generation can.

### Recovery-safe owner PTT-OFF

Generation grants authority to activate; it never grants authority to keep an
exact current session audible. An authenticated owner OFF may therefore carry
the previous generation when recovery advances before the browser receives a
new status snapshot. Django and the engine still require the strict request
schema, current engine instance, fresh timestamp, exact live attempt and user,
browser control-key proof, signed command integrity, current
`remote_dj.mic_gate` authorization, and monotonic sequence ordering.

An executed OFF advances the last sequence, clears `gate_desired`, closes the
physical gate and releases microphone-owned Manual state. Recovery then cannot
restore LIVE audio contrary to that OFF. A later genuinely fresh authorized ON
with the current generation and a newer sequence works normally; an older OFF
arriving after it is rejected as out of order. Another, replaced or ended
session cannot use this path.

### Fail-closed compatibility

Missing, malformed or legacy generations are refused. A mismatched generation
is accepted only for a fully proven OFF for the exact current session; there is
no permissive fallback for ON:

| Mixed version | Result |
|---|---|
| An r0118 browser page | Omits the generation, so updated Django refuses its PTT requests until the tab is reloaded |
| A new page reading old engine status | No usable generation, so PTT stays read-only |
| An old queued command | Lacks the signed generation field, so the updated engine rejects it |

This is intentional.

### Deterministic test corrections

`RemoteDjGateEngineTests.test_scheduled_access_expiry_refuses_both_directions`
was made deterministic in the original r0119 engineering series.
- **The race:** the engine's mute-floor check (`issued_at_ms ≤ floor`) runs
  before re-authorization. An ON stamped in the same millisecond as the floor
  was therefore refused as `superseded_by_mute` rather than `not_authorized`.
  Both refusals are safe.
- **The fix:** the test now pins both orderings with zero-effect snapshots and
  asserts the safety invariants directly.

The final corrective pass also pins the follow-up OFF in
`test_dj_cannot_reopen_while_latched` strictly after the Emergency Mute floor.
That removes a same-millisecond outcome race while retaining assertions that
the physical and desired gates stay OFF, mic-owned Manual is released and the
emergency latch remains set.

- No production behaviour changed.

## Migration and operational scope

There are no new or modified migrations since r0118, so there is no manual
operation and no companion.

Restart, in protected order:

1. `isadoraair-gunicorn`
2. `isadoraair-engine`

The engine restart ends any Remote DJ session and briefly interrupts and then
resumes playout. Install only in a maintenance window with no Remote DJ
connected. KOGR and WRJE remain separate, individually authorized Update
Center operations.

## Resolved PTT-OFF recovery race

The first r0119 candidate documented a narrow regression: an owner OFF pressed
after recovery advanced the engine generation but before the browser observed
it could be refused, allowing recovery to restore LIVE. The final engineering
correction resolves that case with the asymmetric contract above. Permanent
endpoint-to-engine and dual-browser regressions prove that the original
observed binding is retained, the accepted OFF executes after the engine has
advanced, recovery remains silent, and a later fresh ON still works.

- a delayed old request reaching Django after Disable→Enable gets HTTP 409
  `stale_generation`;

  refused `stale_generation`;

  advances, executes, and prevents recovery from restoring LIVE;
- duplicate, delayed and reordered OFF/ON commands preserve later valid intent;
- stale OFF from another session or engine instance and revoked authorization
  remain rejected;
- a fresh authorized press bound to the current generation is applied afterward.
