## What changes

r0121 extends Roadmap 2.27's best-effort causal evidence to three additional
events:

- a completed **Start Next** fade;
- an **automatic skip** because scheduled media is missing; and
- a confirmed **media failure** before air or after playback began.

The original shorter web-request substitution and completed operator Eject
causes remain unchanged. The runner now handles five independent cause
switches, and mixed-cause proposals remain fail-closed unless every cause type
is enabled.

The release also includes bounded hardening accepted during r0121 engineering:

- F2-F4 cleanup, including accurate Web Requests documentation and a read-only
  Hour Refill admin view for users without change permission;
- qualify-before-deduplicate ordering for automatic failures, so a stale or
  ineligible event cannot consume the identity of a later qualified event;
- Start Next and shutdown/install safety corrections;
- exact-path historical r0119/r0120 release-test isolation and inherited test
  fixture corrections; and
- the iPortal workstation clock's `:60` display correction.

The October 29 06:00 pair-landing alert is a separate P2 observability follow-up
and is not changed or claimed fixed by r0121.

## Everything remains Off

Installation creates no `HourRefillPolicy` row. A missing row means Off. If an
operator later creates one, all of these defaults remain conservative:

- `enabled = false`;
- request-substitution, operator-Eject, Start Next, automatic-skip, and
  media-failure capture switches are all false;
- `dry_run_only = true`; and
- `HOUR_REFILL_INSTALL_ARMED` is absent/false unless separately configured.

No migration arms a host, enables a policy, or activates observation or
installation. r0121 publication and installation do not authorize Hour Refill
activation at KOGR or WRJE.

## Provisional thresholds are not approvals

The implemented thresholds remain policy proposals for a later, station-
specific activation decision:

- Start Next-only shortages must be strictly greater than 30 seconds.
- Any qualifying automatic skip or media-failure cause requires a net shortage
  strictly greater than 60 seconds.

These values are **not approved for live use by r0121**. Existing request and
Eject rules retain their r0120 status. Category audit, shadow evidence, timing
review, host arming, and install mode still require separate approvals for each
station.

### Why Tier 1 remains `additive`

Migration-time defaults populate the new NOT NULL columns, while the remaining
new columns are nullable. Existing rows therefore remain valid. The
choices-only field operations emit no SQL, and the constraint replacements
broaden the accepted cause types and add checks that apply only to the new
types. There is no data migration or backfill. This Tier 1 declaration means
the r0120 application can keep running through the forward migration in the
intended feature-Off state; it is not blanket write compatibility for every
later rollback configuration, nor a claim that the seven constraint operations
are mechanically allowlisted.

### Evidence-preserving rollback

Once 0097/0098 evidence exists, reversing either migration can be refused when
the older known-type constraint is restored. Despite 0097's historical header
comment, deleting evidence to make a reverse migration pass is prohibited as a
routine rollback prerequisite.

A source rollback must leave the 0097/0098 schema and append-only evidence in
place and is a separately reviewed recovery path. The new NOT NULL columns do
not retain database defaults, so r0120 source has no blanket write-compatibility
guarantee. In the intended feature-Off/no-policy-row state it does not normally
write the affected rows, but best-effort capture failure cannot be treated as
universally harmless under every configuration. Destructive schema reversal,
forward-only recovery, or restoration of a pre-migration backup remains a
separate operator decision.

## Release authority

Each station requires explicit installation authorization and the normal
trusted Update Center workflow. The companion is central reviewed metadata; it
does not install, enable, or activate anything. Do not substitute a manual
`manage.py migrate`, local approval, or ad-hoc migration edit for a failed
trusted plan.
