## Release notes

### New

- **Managed Active Messages worker** — a new systemd service,
  `isadoraair-active-message-worker`, runs the active-message loop
  continuously instead of on demand. It materializes the one due
  occurrence, asks `isadoraair-render` for its exact aggregate and binds it
  (`PENDING_RENDER → READY`). **With native airing closed it never
  publishes, never sends an engine command, and nothing airs.**
- **Durable worker heartbeat (schema 2) and crash recovery** — the worker
  writes a strictly validated heartbeat to
  `/run/isadoraair/active_message_worker.json` after every pass; a crash at
  any point resumes the same work on restart; repeated unclean restarts are
  recognized as a crash loop.
- **Process-identity supervision** — a heartbeat counts only when it was
  written by the exact process systemd is running (MainPID and its start
  time); a file left by an earlier process never stands in for the worker.
  A start-up gate makes `enable --now` (and every start) complete only once
  that process has written a valid heartbeat and finished its first pass.
- **Monitoring integration** — a new "Active Message Worker" Monitoring
  check (provisioned by `monitoring.0014`) reports `ok`, `warning`,
  `critical` or `unknown` from the unit state, the restart count and the
  verified heartbeat, with notifications after two consecutive bad polls.
  There is deliberately no Restart button for this worker.
- **Operator Board diagnostics** (`/iportal/messages/board/diagnostics/`,
  read-only) — the worker exactly as Monitoring last validated it (process
  identity verified / not current / unknown; heartbeat current / stale /
  missing / unknown), with any incomplete, contradictory or future-dated
  Monitoring evidence shown as "Monitoring status unavailable", never as a
  healthy worker. A reconciliation of Active Messages publications runs
  only on an explicit request (`?inspect=1`), never on a plain visit or a
  status poll.
- **Historical publication and air evidence** on each airing's detail page —
  publication, retirement, insertion and play evidence, kept after
  retirement.
- **Long-session board reliability** — the live status refresh has no
  90-refresh cutoff, keeps one request outstanding, backs off to at most
  five minutes during outages, stops on session expiry, and never asserts
  ON AIR from a stale view.
- **Retention and reconciliation tooling (manual only)** —
  `manage.py active_message_retention` (dry-run by default) and the
  reconciler, with a cleanup quarantine and a Track write guard so a library
  Track can never be left pointing at a removed publication file. **Nothing
  is scheduled**: no timer, no automatic retirement or deletion.

### Feature gates and defaults

| Gate | State in r0116 |
| --- | --- |
| Native Active Messages airing (`NATIVE_AIRING_AVAILABLE`) | **False** (a source constant); Replay Now stays unavailable; OGRemote remains the broadcast authority |
| Automatic publication retirement / retention sweeps | **not scheduled** — operator-invoked command only |
| Worker restart from Monitoring or the board | **not offered** (`restart_via_dashboard = False`; the board has no control) |

A healthy worker does not mean anything is on air; worker infrastructure
readiness confirms nothing about broadcast airtime.

**The runtime-12 bridge rule.** The station's *installed* runtime 12
plans r0116 first. Its generation-14 policy does not know the worker, so:

- the worker is declared in `systemd_units_new_required` (a new file), never
  in `services_requiring_restart`. Runtime 12 refuses a manifest that names
  the worker as a restart ("unknown service"); its plan is
  `isadoraair-gunicorn`, `isadoraair-monitoring`;
- for a plan that crosses a protected-runtime release, runtime 12 defers the
  unknown-unit check to the handoff, where the candidate's **signed**
  generation-15 policy must name the worker (and the manifest must declare
  it) before activation is even requested; without that signed policy the
  job fails closed;
- after generation 15 is active, runtime 13 installs the unit and runs
  `enable --now` once (ENABLE_NOW: install, `daemon-reload`, `enable --now`,
  verify). Only releases **after** r0116 may declare the worker's restart.

All of the above was exercised with the installed runtime-12 code itself
(exported from published r0115) against the r0116 chain.

## What the update does

Planned by Update Center from r0115 (the protected updater's own order):

| Step | Action |
| --- | --- |
| 1 | Trusted source fetched; plan validated (runtime 12) |
| 2 | Protected-runtime handoff: stage, verify (signed attestation, threshold 1) and activate generation 15; the job continues under runtime 13 |
| 3 | Stage the exact r0116 release target; target migration probe; validate the r0116 companion |
| 4 | Database checkpoint (`pg_dump`) |
| 5 | Apply `monitoring.0014` as one guarded atomic migration; re-probe: schema clean |
| 6 | Checkout fast-forward r0115 (`fd3ac80`) → r0116 (`git merge --ff-only`) |
| 7 | No collectstatic (no static file changed) |
| 8 | Install `isadoraair-active-message-worker.service`, `daemon-reload`, `enable --now`; the unit's start gate must pass (≤ 90 s) |
| 9 | Restart `isadoraair-gunicorn`, then `isadoraair-monitoring` |
| 10 | Postflight: exact checkout, clean schema, Gunicorn health |

**Restarts and why:** Gunicorn serves every changed surface (board,
diagnostics, airing evidence, `active_messages.services`, the Track write
guard); Monitoring loads the new worker probe.

**Not restarted, deliberately:** `isadoraair-engine` imports Active Messages
only through `active_messages.playout` and calls only `admit`,
`authorize_open`, `engine_started`, `inspect`, `record_insertion`,
`report_not_aired`, `sync_for_log_item` and `is_candidate` — none of which
takes the publication destination lock, the only playout change in r0116;
with native airing closed those paths are inert. The running r0115 engine
code stays fully compatible and nothing on air is interrupted. The spoken
render worker writes only `<category>/spoken-<uuid>.flac` Track paths,
which the Track write guard never judges. `isadoraair-render`,
`isadoraair-validation`, encoders, RBDS, OGRemote and Weather/AMBER run no
changed code.

## The new service

| Property | Value |
| --- | --- |
| Unit | `isadoraair-active-message-worker.service` (`Type=simple`) |
| Command | `@@ISA_ROOT@@/venv/bin/python @@ISA_ROOT@@/manage.py active_message_worker` (the station's own environment; no shell) |
| Account | the station user (`@@ISA_USER@@`), `WorkingDirectory=@@ISA_ROOT@@`, `EnvironmentFile=@@ISA_ROOT@@/.env` |
| Start gate | `ExecStartPost=… active_message_worker_ready --pid ${MAINPID} --timeout 45`; `TimeoutStartSec=90` |
| Restart | `Restart=on-failure`, 10 s growing to at most 2 min; never a tight loop |
| Stop | SIGTERM between passes, `TimeoutStopSec=30`; an interrupted render is redone on the next start |
| Ordering | `After=` / `Wants=` `isadoraair-render.service isadoraair-validation.service` (no `Requires=`; a renderer outage is retryable work) |
| Hardening | `NoNewPrivileges`, empty capability sets, `PrivateTmp`, restricted address families, kernel/clock/hostname protection |
| Coupling | none to OGRemote, the engine, encoders or the audio chain: a failed worker affects no other unit |

## Forward-only release and recovery

Update Center promises **no automatic rollback** (docs/UPDATE_CENTER.md,
"Failure, retry, and rollback"). Generation 14 stays the last-known-good
protected slot until generation 15 commits.

| Failure point | State and supported handling |
| --- | --- |
| Before the handoff (step 1) | Production unchanged. Retry. |
| During the handoff (step 2) | The supervisor's own activation contract: either generation 15 is accepted and the same job resumes under it, or generation 14 stays active and the job fails with evidence. Never replace runtime slots by hand. |
| Before the migration (steps 3–4) | Generation 15 active; application unchanged. Retry. |
| During the migration (step 5) | One guarded atomic migration: it either inserted the check row or did not. Manual intervention with evidence on an ambiguous interruption. |
| After the migration, before source advancement (step 6) | The check row exists while r0115 code (and r0115 Monitoring) still runs: Monitoring may report the not-yet-installed unit as inactive (an alert, no broadcast effect). Retry; fix the cause (see the installation document's checkout preflight). |
| After source advancement, during unit start (step 8) | Checkout at r0116; if the start gate fails the job fails **before** any declared restart and touches no other unit; the unit stays enabled and retries with back-off — harmless with the gate closed. Fix forward. |
| During restarts / postflight (steps 9–10) | `failed` / `manual_intervention_required` with evidence; fix forward. |
| After postflight | Installed. Fix forward with a corrected signed release. |
| Full pre-upgrade restoration | Only as disaster recovery restoring code and database together from the step-4 checkpoint through the approved procedure, with Recovery Assurance afterwards — never a code-only revert, never a hand-edited unit, policy, trust file or migration. Refresh the Runtime Recovery payload for generation 15 after installation. |

Operator installation preflight and acceptance: `docs/releases/r0116_installation.md`.
