## What r0120 does

When an eligible event leaves the current hour's log short, r0120 can
**propose**, and once separately armed and enabled **install**, up to two
music tracks (plus an optional residual PSA) so the hour still reaches its
boundary.

**Everything ships Off.** After installation:

- no `HourRefillPolicy` row exists. Nothing creates one on install, and a
  missing row means Off;
- the master switch and both cause-type switches are Off;
- **Observation only (dry run)** defaults to checked;
- `HOUR_REFILL_INSTALL_ARMED` is absent from every station `.env`, which means
  not armed;
- `HOUR_REFILL_PSA_CATEGORY_ID` is absent, which means the residual PSA is Off.

While Off, the engine's runner thread makes one primary-key read every 15 s
and does nothing else. No cause is recorded, nothing is proposed or written,
and no `Hour-refill evaluation` journal line is emitted.

### Causes in scope (version 1)

- A completed, eligible **operator Eject** of a scheduled music occurrence.
- A **shorter web-request substitution** of a scheduled music occurrence.

**Not** causes in r0120: Start Next, automatic skips, missing or unreadable
media, and any other playback failure.

Cause capture is best-effort. A failed capture never blocks the Eject or the
substitution, and is counted rather than retried.

### Rules (provisional, for field verification)

- **Threshold on the combined net hour deficit**, strictly greater than:
  - more than 30 s for Eject-only cause sets;
  - more than 60 s when any qualifying cause is a request substitution.

  Exactly 30.000 s or 60.000 s does not qualify.
- **Selection:**
  - at most **two music tracks**, from the causes' scheduled categories or the
    last remaining music row's category;
  - full category separation, plus hard exclusions for the log, decks, forced
    items, pending requests and the next hour;
  - an optional residual **PSA** only after a music fit, with a residual of at
    most 60 s, never alone. It is disabled by default.
- **Protected closing blocks.** Legal ID, PSA, underwriting and imaging rows at
  the end of the hour stay last. A refill is inserted before them, never after.
  This depends on correct category-kind filing, which is checked in the
  separate rollout audit.
- **Timing:**
  - a 20 s minimum lead between the second snapshot and the trigger that reads
    the first inserted row;
  - a provisional safety budget of **5 s + 1 s per inserted item** left over
    after the fill.

  Neither is a proven universal bound. The rollout packet requires as-run
  timing evidence before install mode.
- **No false air evidence.** A committed install is recorded as *committed*,
  not *aired*. "Aired" is only ever shown from an existing `PlayEvent` of an
  inserted row.

### Gates for install mode (all required; none set by this release)

1. Migration `library.0096` applied: the Phase A database constraint forcing
   dry run is removed.
2. `HOUR_REFILL_INSTALL_ARMED=True` in that station's `.env`, then a restart.
3. Policy master switch On with **Observation only** unchecked.
4. Every qualified cause type's switch On. A mixed cause set is never trimmed to
   a subset.

The installer re-reads the policy under a row lock inside the install
transaction. Turning the switch Off or re-checking dry run stops the next
install without a restart.

### Tier 1: why `migration_compatibility` is `"additive"`

Tier 1 is the release author's reviewed declaration that the migration work is
backward compatible with the data and with the r0119 code that keeps running
until the restarts. It is **not** a claim that every operation fits the
mechanical Tier 2 allowlist. Two operations do not, and the companion covers
them.

- **0093 and 0095** create new tables only. The r0119 code never reads them.
- **0094** adds a nullable column with no default. r0119 inserts omit it and
  get `NULL`.
- **0095's AlterField** changes `choices` only. It emits no SQL.
- **0096's RemoveConstraint**:
  - emits exactly
    `ALTER TABLE "library_hourrefillpolicy" DROP CONSTRAINT "hour_refill_policy_dry_run_only_phase_a"`;
  - only relaxes a CHECK, so every existing row stays valid;
  - updates and deletes no row;
  - touches a table the r0119 code does not know exists.
- **0096's AlterField** changes `editable`, `verbose_name` and `help_text`
  only. It emits no SQL. There was never a database-level default (the
  default `True` is supplied by Django on insert), and none is added.

No data is lost, rewritten or made unreadable, and old code keeps working
against the new schema. That is the compatibility the declaration asserts.

**What 0096 does change is an operational barrier.** The removed constraint
was the database-level guarantee that no policy could leave dry run. After
0096, that guarantee moves to the remaining application gates above, all of
which stay Off. Because a safety-enforcing barrier is removed, its two exact
operations are not accepted mechanically. They were reviewed at release time
and are authorized only by the trusted r0120 companion, pinned to `0096`'s
exact bytes and operation indices.

**Reverse.** `0096`'s reverse re-adds the CHECK and succeeds only while every
policy row has `dry_run_only = True`. Source rollback does not reverse
migrations. See the installation guide.

### Trusted migration-authorization companion

`deploy/migration_authorizations/r0120.json` binds:

- r0120's release-introducing commit;
- the SHA-256 of `deploy/releases/r0120.json` at that commit;
- exactly two operations:
  - `library.0096_hour_refill_install_gate` index 0, `RemoveConstraint`;
  - `library.0096_hour_refill_install_gate` index 1, `AlterField`;
  - both classified manual, at `0096`'s exact file SHA-256.

It authorizes nothing else. If a station's own derived plan contains any other
manual operation, or `0096`'s bytes differ, central coverage fails. The station
then stops for exact local review. The companion is trusted release metadata
inherited from the root-configured, fast-forward-only trusted repository. It
is not a cryptographic signature.

An operator must still start the Update Center installation on each station.
The companion does not install anything by itself and does not enable 2.27.

## Restarts and operational scope

Restart, in protected order:

1. `isadoraair-gunicorn`: admin, views and settings changed.
2. `isadoraair-engine`: the engine hosts the runner thread and cause capture.

The engine restart briefly interrupts playout and ends any Remote DJ session.
Install only in a quiet maintenance window, with no Remote DJ connected.

The web-request reconciler (`refresh_song_request_statuses`) runs as a fresh
process on each poll, so it needs no restart. No other service is restarted.
r0120 adds no unit, timer, package, static asset, nginx change or
protected-runtime change.

## Not authorized by this release

r0120 does not authorize installing at any station, and neither does the
automatic `0096` migration. It also does not authorize:

- arming any host;
- enabling observation or install mode;
- residual PSA.

Each of these is a separate later decision, following
`docs/roadmap/2_27_PHASE_D_ROLLOUT_PACKET.md`. KOGR goes first and WRJE
decides independently.
