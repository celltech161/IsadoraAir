# r0130: Category Drift Remediation

r0130 lets an authorized **Manage tracks** operator repair *category drift* — a Track whose file sits in a
Library folder other than its primary Category's — from **Library → Reconciliation**, and optionally move files
when changing primary Categories in the **/library/** bulk editor.

A Category is a programming decision; a folder is a storage location. When they disagree, the operator decides
which one is right. A drift finding alone does not prove whether the database Category or the physical folder is
wrong. Nothing is chosen, moved, imported, deleted or inferred automatically.

## Reconciliation Option A — Move file

* **Category kept:** the existing primary Category stays.
* **File moved:** the file moves into that Category's folder, `LIBRARY_ROOT/<Category code>/<the same file name>`,
  and the Track's registered filepath is updated to match.
* **Preserved:**
  * the Track's metadata;
  * primary and additional Category memberships;
  * holidays and readiness;
  * cue markers, their locks and approvals;
  * play history, logs, playlists and VoiceTracks.
* **Audio:** moved as the same file, not re-encoded, retagged or copied.

## Reconciliation Option B — Change Category

* **File left in place:** the file is not moved, transcoded or rewritten.
* **Category matched:** the primary Category becomes the *existing* Category whose code exactly matches the
  file's folder. No Category is ever created or guessed from artist, genre, album, file name or tags.
* **Preserved:** unrelated metadata. An additional membership that would duplicate the new primary is dropped.
* **Old primary:** carried into additional Categories only when the operator explicitly selects that option;
  the preview shows it and the audit records it.
* **Warnings:** the preview warns when the content kind changes, and states that future scheduling will select
  the Track under its new Category while entries already in approved logs are not changed.

**C — No action** is the default for every finding.

## Bounded, reviewed batches

* **Filtering:** findings can be filtered by current folder and primary Category and grouped by mismatch.
* **Batch size:** at most one page (25 findings) can be selected for one explicitly chosen direction; there is
  no "fix all".
* **Preview:** rechecks everything against the Library as it is now. It reports per-Track details and totals
  (eligible, refused, expected moves and Category changes, collisions, scheduling conflicts, files requiring
  review), and issues one token per eligible repair. Each token is:
  * signed, bound to the operator and to the sign-in session that previewed it;
  * expiring, and single-use;
  * bound to the exact Track, direction, source file identity and destination or target Category.
* **Apply:** the operator confirms, and the page sends one repair per request. It stops at any lost or 5xx
  answer, `uncertain` or `committed_cleanup_required`, and never retries. The selection is cleared afterwards;
  review the current state before another batch.
* **Older reports:** reports made before r0130 do not contain the evidence a repair needs and stay review-only.
  Run a fresh reconciliation scan; installation does not start one.

## Bulk Category editing

**Choosing the policy.** *Set primary category* now asks what happens to the files:
* *Update Category and move files to its folder* — the recommended, default choice in the editor.
* *Update Category only* — leaves file locations unchanged.

**Move-enabled mode:**
* *Explicit confirmation is required.* The page always asks for it, and the server rejects an apply without
  `confirm_move: true` before the preview is used.
* *Checked at preview.* Every planned move is checked and listed.
* *All or nothing per Track.* A move that fails changes nothing for that Track; there is **no automatic fallback
  to database-only editing** after a failed relocation.
* *Limits.* At most **25 file moves** per bulk edit; the 1,000-Track selection limit is unchanged.
* *Results.* Per-Track partial-success reporting: moved, refused, stale, failed, cleanup-required, uncertain and
  not-attempted Tracks are reported separately. Any outcome that needs the operator stops the remaining Tracks.

**Compatibility.** The existing metadata-only API behaviour remains available: a request that omits
`file_location` behaves exactly as in r0125, with its warning that files stay in their previous folders. Clearing
the Category never moves a file.

## Media protection

One shared, guarded relocation service performs every move, for Track Detail, Reconciliation and the bulk editor.

* **Source identity verification.** The file must still be exactly the file the scan or preview recorded:
  * the same path, with its six-field witness (device, inode, size, mtime, ctime, link count);
  * a canonical, non-empty, readable regular file inside the Library;
  * not hard-linked, not changed within the last minute (in delivery), not owned by the spoken projection or
    Active Messages, and not remote-hosted.
* **Fixed destination identity.** The destination's expected identity comes from creating it (the inode of a
  descriptor held open throughout), never from a later look at its name. It is rechecked immediately before the
  database commit.
* **Destination collision refusal.** An existing file, or another Track's path, at the destination is never
  overwritten, renamed or numbered.
* **Current and on-air protection.** A Track on a deck, in the engine's queue, claimed by the engine, recently
  started, or in an unplayed entry of the current or next log hour or the engine's active log is refused. So is
  every Track when the engine's state cannot be confirmed. Retry later. Later approved logs are only reported.
* **Bounded locking.** Path locks first, then the Track row, with bounded waits; contention is reported as busy
  and changes nothing.
* **Transaction-aware results.** Every outcome is audited (`relocation.track`), with the operator, origin,
  Categories, paths, commit and cleanup status:

  | Outcome | Meaning |
  |---|---|
  | `moved` / `updated` | Ordinary success: the old entry was cleaned up, or no file was involved. |
  | `committed_cleanup_required` | The move committed and is valid; the old directory entry needs operator attention. |
  | `uncertain` | The database did not confirm the commit; both directory entries were kept. Inspect before doing anything else. |

## Waveform-cache consequence

**A successfully relocated recording retains its existing waveform and cue markers, but its waveform cache may
become unverified because the recorded source path has changed.**

* **Still playable.** The recording plays normally.
* **Some editing waits.** Cue-point operations that need a verified waveform (Repick, Reset Cue Points) are
  unavailable until a subsequent **Reanalyze Track**.
* **No automatic reanalysis.** r0130 does not reanalyze relocated Tracks; reanalyze only the Tracks whose cue
  points you need to edit.

## Quarantine and recovery

* **The directory.** `.relocation-quarantine/` beneath the Library root is a private, managed directory (mode
  0700). Removing a file entry first moves it there atomically, without overwriting, and checks its identity;
  only the expected file is deleted, inside the quarantine.
* **Retained files.** Safe cleanup can **retain** a file when its identity, or its restoration to its original
  place, cannot be established. `RETAINED.json` beside it records its original path, role, expected and found
  identity, and reason. The result and the audit event give its location.
* **What to check.**
  * `committed_cleanup_required` and `uncertain` require operator inspection.
  * Never automatically retry an uncertain relocation.
  * Do not manually empty the quarantine without resolving its retained objects and their ownership.
* **Three different situations:**
  * *Ordinary cleanup:* the old entry was removed and nothing remains in the quarantine.
  * *Committed but incomplete cleanup:* the Track is valid at its new path, but an old entry or a retained
    object needs attention.
  * *Uncertain database commit:* whether the Track was updated is unknown, and both entries exist.

## Platform requirements and limitations

* **Linux filesystem support.**
  * Identity-safe removal needs Linux `renameat2(RENAME_NOREPLACE)` (glibc) on a filesystem that supports it
    (ext4, xfs, btrfs and tmpfs do).
  * The quarantine must be on the same filesystem as the entry being removed.
  * Where any of these is unsupported, removal **fails closed**: nothing is removed and the entry is reported
    as retained.
* **Cross-filesystem moves.** Reconciliation and bulk relocation refuse to move a file across filesystems. Track
  Detail keeps its existing cross-filesystem copy fallback, now verified by reading the copy back, along with
  its previously documented limitation: the copy is not time-bounded, and a web-worker timeout during it can
  leave a partial copy, though never alter the original.
* **What is and is not guaranteed.**
  * IsadoraAir serializes its own cooperating operations with transaction-scoped path locks, and its relocation
    cleanup never knowingly deletes a substituted, unrelated file.
  * A non-cooperating external writer can still independently delete a registered recording.
  * An external unlink between the last-link check and the cleanup can leave a recording with no filesystem
    name.
  * No atomic guarantee against that is claimed. Backups remain the protection against external deletion.

## Deployment declaration

* **Migration:** none; no migration-authorization companion exists or is required.
* **Python requirements and APT packages:** unchanged.
* **Systemd and protected runtime:** no unit, timer, policy, descriptor, attestation or protected
  generation change. `protected_runtime` is `null`, so no offline release signature is created.
* **Static and nginx:** unchanged (templates only, no static asset); no `collectstatic` action.
* **Restart:** Gunicorn only (`isadoraair-gunicorn`).
* **Not restarted:** engine, encoders, Monitoring, RBDS, Active Messages, reconciliation processes, spoken
  rendering and every other station service.

Publishing r0130 does not authorize installation at KOGR or WRJE, a production reconciliation scan, a
relocation or a Category change. See [r0130_installation.md](r0130_installation.md).

## Not completed by this release

r0130 does not complete all of roadmap 3.11. After publication, Category Drift Remediation may be recorded as
engineering-complete. Separately scoped and still open:
* unregistered-file remediation;
* uncertain-finding remediation;
* the remaining Library reconciliation classifications;
* Library lifecycle policies;
* the separately gated waveform-orphan cleanup.

This release adds no automatic relocation, import, deletion or Category inference, no scanner daemon or bulk
reanalysis, and no engine, encoder, scheduler or playout change. It does not change the DST fall-back item, Hour
Refill or native Active Messages airing.
