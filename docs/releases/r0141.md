# r0141: Past Overrides, NEXT relocation and live queue Track Swap

r0141 delivers three operator-facing enhancements and the engine safety changes that make the third one safe:

1. **Past Overrides** in Schedule → Date Override;
2. a new Console queue column order with **NEXT** beside the drag handle;
3. a guarded live **Swap** that replaces the track of one eligible upcoming queue occurrence in place;
4. engine changes: the playback claim adopts a committed Swap atomically, and live-fill proposals are revalidated
   against the committed queue under the log lock.

The release has **no migration** and requires restarting `isadoraair-gunicorn`, then `isadoraair-engine`. **The
engine restart interrupts program audio and ends any live Remote DJ session.** Publication does not authorize
installation at KOGR or WRJE; see `r0141_installation.md`.

## A. Past Overrides

**Where.** Schedule → **Date Override** mode has a new **Past Overrides** button to the right of the date controls
(after **Today**). It replaces the 24-hour day view with a list; choosing a date or switching back to Weekly Schedule
leaves it.

**What it lists.** The selected **Schedule Profile's** stored, explicit date rows (`ScheduleBlock` rows with a
`specific_date`) dated **before today** in the **station timezone**, newest date first. Today's and future overrides
are not listed. It reads stored rows directly, never weekly rows and never the inherited or effective resolution, so
**every explicit transition is listed, including transitions at minutes other than `:00`**. It answers "which old
date still references this Rotation or Playlist?", for example when a Rotation cannot be deleted because a forgotten
dated override still protects it.

- **Search / filter:** the filter field narrows the list by Rotation or Playlist name (`?q=`).
- **Date-grouped pagination:** whole dates per page (default 30, at most 100), so one date is never split;
  **Load older dates** continues from the last date shown.
- **Show date / Show hour:** returns to that date's 24-hour view and highlights the hour; a transition inside the
  hour also opens Hour Detail.
- **Remove:** an explicit override deletion. A confirmation names the date, time, content and profile; the request
  reuses the existing scoped `DELETE /api/schedule/<id>/?profile=&date=` and deletes exactly that one dated row.
- **Authorization and protections are unchanged:** the list has the same access as the other schedule reads;
  Remove requires `schedule.edit`, and **archived profiles are refused**.
- **Preserved:** Remove never deletes other dates, sibling transitions, the recurring **weekly schedule** or
  **generated logs** (no log references a `ScheduleBlock`).
- **Removing a date override does not delete its Rotation or Playlist.** A content item can be referenced by several
  dates and several profiles; it becomes deletable, through its own normal deletion, only once every reference is
  gone.
- Switching profile, mode or date discards any in-flight list request, so a late answer never renders for the wrong
  profile, filter or mode.

The endpoint is `GET /api/schedule/past-overrides/?profile=<uuid>&limit=&before=&q=` (read-only).

## B. Console queue controls

The Console and `/remote-dj/` "Coming Up" table columns are now:

**Drag | NEXT | Swap | # | Artist | Title | Cat | Dur | Intro | Time On**

- **NEXT keeps its previous behavior**: the same pill, icon, `setNext()` request (`POST /api/engine/queue/set-next/`)
  and stale-connection gate. Only its column moved.
- The **existing drag-to-reorder mechanism is unchanged**. Dragging starts only from the handle; pressing NEXT or
  Swap never starts a drag.
- NEXT, Swap and the drag handle appear only on upcoming rows. Played, on-air and on-deck rows carry none of them.
- **Keyboard focus:** the queue table is rebuilt every second; keyboard focus now stays on the same row's control
  (NEXT or Swap) across that redraw instead of dropping to the page.

## C. Live Track Swap

The Swap button (two opposed arrows) replaces **one upcoming occurrence's track in place**.

1. **Dialog and search.** Swap opens a dialog bound to that row, showing the target and a search field. The search
   is the same request, Ready to Air filter and result summary as **Search to add track**.
2. **Replacement preview.** Choosing a result shows the target and the replacement side by side with the **planned
   effective-airtime** change, read from the server (`GET /api/engine/queue/replace/?item_id=&track_id=`, read-only,
   same authorization as Swap).
3. **Confirmation before mutation.** Nothing changes until **Swap track** is pressed. Cancel or Escape changes nothing.
4. **Server validation.** `POST /api/engine/queue/replace/` (CSRF, `playout.queue_manage` under the schedule policy)
   re-checks everything the browser showed: the engine's published state must be fresh and from the **same engine
   instance**, list the row in its live upcoming queue and not hold it on a deck; then, under row locks, the row must
   still carry the **expected track**, be unplayed and **unclaimed**, in an approved log, an eligible music slot and
   not reserved by a listener request; the replacement must be ready to air, music, with its media file present.
5. **Identity preserved.** Only `track`, `track_title` and `track_artist` change (the same three fields a Web
   Requests swap writes). The `LogItem` id, position, `scheduled_time`, **category** (the slot's scheduling
   provenance) and **origin** are preserved; nothing is inserted. A repeated request after a committed Swap is an
   idempotent no-op.
6. **Normal queue reload.** The engine adopts the change through its normal ~3 s queue reload, and in any case at the
   claim (below). A deck that already holds a track is never modified.

**Eligible origins.** Only `generated_schedule`, `generated_fill` (build-time fill) and `operator_inserted` music
slots can be swapped.

**Not eligible (refused, nothing changed):** `live_fill` (it may be a deadline-qualified closing fill),
`refill_installed` (bound to its Hour Refill ledger), urgent/engine insertions (`engine_inserted`: urgent alerts,
native Active Messages, dedication intros), DST replay (`dst_replay`) and occurrences with an **unknown or missing
origin**. Also refused: **claimed**, **played** and **on-deck** rows, rows **reserved by a listener request**,
non-music slots and rows outside an approved live log.

**Engine claim-time safety.** Before r0141 the engine opened an occurrence from its in-memory copy, so a Swap that
committed after the last ~3 s reload could be claimed with the stale track. Now `_claim_playback_occurrence` re-reads
the row under the same lock it takes to claim and, if the row is unclaimed and its committed track differs, **adopts
the committed track atomically with the claim** (checked with the ordinary playability gate). However many Swaps
commit before the claim, the claim takes the last one; once claimed, no Swap is accepted. A claim that cannot take
the row lock within 250 ms (a Swap or Web Request is writing the row) is **contended, not failed**: the same
occurrence stays next and is retried (bounded; see Known limitations). Nothing after it is skipped or claimed.

**Effective airtime, conditional fill.** The preview compares **effective airtime** (next start minus cue-in), or
the file length where a track has no next-start marker (stated), or "can't be estimated". When a replacement shortens
the planned airtime, the dialog says IsadoraAir will evaluate the remaining hour with its existing scheduling and fill
rules and that **additional material is not guaranteed**. A Swap itself never inserts filler.

**Unknown HTTP outcomes and Check again.** Only `200 {ok}` is success; any 4xx is a definite refusal (the server
refuses before changing anything). A network error, a 5xx or an unreadable reply leaves the outcome **unknown**:
after a short delay the dialog reads the row's committed state from the database.

- The chosen track confirms the Swap.
- The original track on a row the engine has **claimed or played** is final: not swapped.
- Everything else stays unknown with **Check again**, including the original track on a still-unclaimed row, because
  the lost request may still be running and commit after that read.

There is **no automatic mutation retry**: the POST is never repeated automatically, and Swap track stays hidden while
the outcome is unknown. A new attempt is an explicit operator action (close, reopen, choose, confirm).

## D. Existing Web Requests behavior

A row already reserved for a listener's song request is refused, so no request is unlinked or falsely fulfilled.
However, **a later eligible listener request can replace an operator-selected track before that occurrence is
claimed**: Web Requests scheduling may reserve a swapped music slot (as it can an operator-inserted one), and the
listener's request then replaces the operator's choice. This is the unchanged Web Requests priority and an accepted
limitation. A Swap is **not an operator reservation and carries no priority guarantee**.

## E. Remote DJ access

**Swap is currently unavailable to Remote Hosts.** The seeded `remote_dj` GroupAccess lists exact paths and does not
include `/api/engine/queue/replace/`, so on `/remote-dj/` the Swap button is shown but disabled ("this account's
current access policy does not include it"), and direct requests are denied. **NEXT, queue insert and reorder
permissions are unchanged.** r0141 includes **no GroupAccess migration and no privilege expansion**.

## F. Airtime and refill safety

- **Effective airtime versus file duration.** The engine's committed runway sums the leading deck's remaining playout
  and each future item's effective airtime (`next_start - cue_in`), not raw file durations. A Swap changes only what
  that runway reads after the next reload.
- **Normal fill is unchanged.** The established live fill compares that runway with the time left in the hour when
  the queue runs out and fills only a genuine shortage (or the end-of-hour closing fill), with its existing
  generation, prior-count, Hour Refill coordinator and later-hour guards. If the next hour's log is already approved,
  the existing **next-hour rollover** policy applies instead.
- **Corrected live-fill proposal fingerprint.** A live-fill proposal is now bound to the queue it was computed from:
  the dispatcher records the ordered `(LogItem id, Track id)` queue identity. The installer discards the proposal if
  the in-memory queue differs, then, **in the same transaction as the append and holding the `PlaylistLog` lock**
  (250 ms wait), compares the committed queue (minus poison-guarded rows) and appends only if it is unchanged. A Swap
  committed after dispatch therefore voids the stale proposal; a later dispatch re-evaluates the shortage. A lock
  timeout discards without inserting, and the engine's queue is extended only after the append commits.
- **No guaranteed filler.** When eligible content or time is unavailable, no filler is added.
- **Roadmap 2.27 Hour Refill is unchanged.** Its observation-only operation, `dry_run_only` setting and host-arm
  (`HOUR_REFILL_INSTALL_ARMED`) boundaries are untouched. A Swap is not a `request_substitution` cause and records no
  refill evidence. r0141 does **not** activate Hour Refill, introduces no new refill cause and does not guarantee
  uninterrupted playout under every shortage condition.

## G. Known limitations

**Introduced by r0141 (accepted):**

- **Bounded claim-contention recovery.** A contended claim is retried (one 300 ms retry callback; the crossfade
  trigger may also retry). After **8 consecutive contended attempts** (each waits up to 250 ms, roughly four seconds
  in total) the occurrence is skipped with the Monitoring error event "Occurrence skipped after persistent claim
  contention", naming the row and attempt count; the row stays truthfully unclaimed and unplayed and playback advances.
  The count is per occurrence and per engine process (an engine restart resets it). If that was the hour's last
  occurrence and rollover or live fill cannot supply material, silence remains possible, as it would be when waiting
  indefinitely behind the lock.
- **Swap unknown-outcome reconciliation** reads the committed row once per check; an outcome that stays ambiguous
  requires **Check again** or a look at the queue.
- **Remote Hosts cannot Swap** until an operator decides to grant the path (a separate change).

**Inherited, unchanged by r0141:**

- **Queue-writer concurrency boundaries.** Swap, Web Requests and Hour Refill install take the `PlaylistLog` lock and
  are fully serialized with the live-fill install. Operator **Insert**, **Reorder** and **NEXT** do not take it: a
  change they commit before the install's committed-queue read is detected; one committing in the sub-millisecond
  window between that read and the commit is not. Reorder and NEXT normally preserve total runway; a concurrent
  operator insertion can produce an unnecessary fill or a position conflict (which rolls the fill back), and the
  existing insert path can leave its own row at position 9999 if its repositioning fails.
- **Poison-row / live-fill.** Poison-guarded rows are intentionally omitted from the queue fingerprint. A trailing
  persisted poison-guarded row can collide with the live-fill start position; the append then rolls back cleanly and
  memory is not extended.
- **Web Requests can supersede an operator Swap** before the occurrence is claimed (section D).

**Qualification limits:**

- **No real-engine / GStreamer field acceptance has been performed.** Claim adoption, contention and live-fill
  revalidation were qualified with database-level tests (real PostgreSQL row locks) against the engine's code paths,
  not with a running audio pipeline.
- **The browser harnesses use simulated API responses** (host Chromium against the real rendered pages; engine
  status, search, Swap and preview requests are deterministic fakes). They do not prove GStreamer playout.

## Engineering qualification

Codex completed an independent adversarial review of the candidate `9f230bf` (findings F1–F5), a review of the
corrected candidate `9b83a45` (F1–F4 fixed, F5 partially fixed) and a focused re-review accepting the F5 correction
`d0aa0f2` for release engineering.

- **Adversarial negative controls:** the same three behavior-only reproductions (repeated Swap during adoption, a
  row lock held past the claim timeout, a stale live-fill proposal) fail 3 of 3 on `9f230bf` and pass 3 of 3 on the
  corrected candidate.
- **F5 browser negative control:** the corrected unknown-outcome checks pass 7 of 14 on `9b83a45` (reproducing the
  false "Not swapped" state) and 26 of 26 on `d0aa0f2`.
- **Browser harnesses at `d0aa0f2`:** Console 96 of 96 checks; Schedule (Past Overrides) 35 of 35.
- **Full `library` + `authz`:** **not clean** on either side. r0140 reported 3,871 tests and 452 failure/error
  identifiers; the corrected candidate 3,944 tests and 451 identifiers, with **no candidate-only identifier** (the one
  r0140-only identifier is the known intermittent undecodable-media test). They are environmental and inherited
  (Playwright browsers cannot launch inside the guarded sandbox, `MediaRejected` media fixtures, read-only media
  paths); r0141 neither introduces nor corrects them. At `d0aa0f2`, every library module that reads the Console
  template plus the Swap suites reproduced the same identifiers exactly.
- **Web Requests + Active Messages:** 888 tests, 205 identical failure/error identifiers on r0140 and the candidate
  (inherited, not clean).

## Deployment declaration

There is no migration: `migrations_required` is empty and `migration_compatibility` is `null`. Restart exactly, in
this order:

1. `isadoraair-gunicorn`
2. `isadoraair-engine`

Gunicorn serves the changed views, URLs, templates and the new Swap service; the engine runs the changed claim and
live-fill code (`library.services.engine`, `library.services.log_builder`). No other long-running service loads the
changed code. There are no new packages, Python requirements, static assets, collectstatic, nginx changes, systemd
units, manual bootstrap or protected-runtime changes: `protected_runtime` is `null`.

**The engine restart interrupts program audio and ends any live Remote DJ session.** Installing r0141 does not delete
any schedule override, Rotation or Playlist, does not enable Hour Refill and does not change Web Requests priority or
Remote DJ permissions. Publication does not authorize installation: each station requires separate preflight,
installation authorization and operational acceptance; see `r0141_installation.md`.
