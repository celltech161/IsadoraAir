# r0133: Update Center refuses an inconsistent migration history

r0133 is a narrow safety release for the Update Center. It adds no setting, migration, package or service, and it
changes nothing about playout, scheduling, Web Requests, Remote DJ or Hour Refill.

## Problem corrected

Every Django migration is recorded in the database when it is applied. If the record for an older migration goes
missing while a later migration that depends on it is still recorded as applied, the database history is
inconsistent. The Update Center did not notice. Its check only asked which migrations were still pending, and it
skipped any newest migration it believed was already applied without looking at that migration's prerequisites. A
database in this state could therefore be reported as schema-current, and the protected migration probe could
produce a migration plan and a trusted plan digest for it.

## New behavior

- The Update Center now asks Django's own consistency check (`check_consistent_history()`) whether every applied
  migration's prerequisites are recorded, before it plans any forward migration.
- An inconsistent history gets its own schema-health status, `inconsistent_migration_history`. It is not treated as an
  ordinary pending migration and carries no pending-migration list.
- Planning becomes non-actionable (`SCHEMA_DRIFT_DETECTED`). The Update Center page shows Django's diagnostic, which
  names the applied migration and the prerequisite that has no record.
- The protected migration probe applies the same check and fails before it builds a plan, classifies migrations or
  computes a plan digest. The protected updater already classifies that failure as `PROBE_FAILED`, so an update stops
  at the pre-advance gate with nothing changed.
- **Nothing is repaired automatically.** Correcting a recorder history is a deliberate, reviewed operator action, not
  something the Update Center does.
- An unexpected failure of the validation itself still reports `migration_state_indeterminate`. It is never treated as
  healthy.

## Unchanged behavior

- A healthy migration history stays eligible for updates.
- A legitimately unapplied migration (a consistent applied prefix with work still pending) keeps its existing
  handling and still appears in the plan, in the same order.
- For healthy histories the probe's payload layout, plan order, manual-operation classification and trusted plan
  digest are unchanged, and existing migration-authorization companions and approval rules remain valid.
- Source/manifest health (`safety_status`) and database schema health stay separate signals.
- No schema or application-data migration is introduced. Normal playout, scheduling, Web Requests, Remote DJ and Hour
  Refill behavior are unchanged.

## Operator impact

This release introduces no new operator-facing configuration. A station with a healthy migration history sees no
difference. A station with an inconsistent history sees `inconsistent_migration_history` on the Update Center page
and cannot plan an update until the history is corrected through a separately reviewed procedure.

## Deployment declaration

There are no migrations, migration companion, packages, Python requirements, collectstatic, nginx, systemd units or
protected-runtime changes. `protected_runtime` is `null`, so no protected descriptor, policy generation, offline
release signature or attestation is created. The only restart is `isadoraair-gunicorn`: the schema-health check is
consumed by the web application, and the migration probe runs as a fresh subprocess from the source tree it is asked
about, so no persistent service needs a restart for it. The engine, encoders, Monitoring, RBDS, Active Messages and
spoken rendering are not restarted. KOGR and WRJE each need separate installation authorization; see
`r0133_installation.md`.
