# r0137: Combined NWS/AMBER spoken alert

r0137 replaces the separate Weather alert and AMBER announcements with one coordinated spoken announcement. The
single canonical file, `WxAlert/wx_alert.flac`, and its one Library Track (title **Weather Alert**) now carry every
currently valid qualifying NWS and AMBER-family alert together. It is an ordinary track inserted at the next track
boundary. It is not an EAS encoder, not a mid-track emergency interruption system and not an audio overlay: nothing is
mixed over, ducked or interrupted, and the Weather Alert Beep is unchanged.

## What changes

### Combined NWS/AMBER spoken alerts

- One combined announcement contains all currently valid qualifying alerts: NWS watches and warnings first, then
  AMBER-family alerts ordered by event and identifier.
- The canonical `WxAlert/wx_alert.flac` file and its Library Track are reused. The retired `wx_alert.mp3` Track is
  never selected by this workflow.
- Change detection uses the effective spoken content: source, alert identity and exact spoken text. Headlines, feed
  order and advisories that are not spoken do not change it.
- An unchanged set of alerts is not spoken again. There is no periodic repetition.
- When either NWS or AMBER content changes, the announcement is rebuilt from both sources and replaces the previous
  one. When nothing remains in effect, any pending announcement is withdrawn.
- `weather_ingest/amber_alert.py` is now a thin wrapper around the one coordinator, `weather_ingest/wx_alert.py`,
  which is the only producer of `wx_alert.flac`. The pollers `update_local_wx_data.py` (NWS) and `amber_poll.py`
  (IPAWS) write validated source snapshots and then run the coordinator.
- The coordinator records its state in `WEATHER_DATA_DIR/wx_alert_state.json`: generation, content fingerprint, the
  published file's identity, validity and source states. Weather Diagnostics reports it.

### Publication and playout reliability

- Audio is published atomically with a last-known-good rollback. Synthesis is all-or-nothing, and a candidate is
  discarded unpublished if the sources change while it is being built.
- Already-open GStreamer decks are protected: a deck keeps the file it opened, and an announcement is not opened while
  a publication is in progress.
- Publication and deck opening are synchronized through the publication lock, and the Track's duration and next-start
  are re-read at the moment a deck opens, so timing matches the audio actually played.
- Urgent insertion of the WxAlert category is idempotent: the engine reads the coordinator record, and at most one
  combined occurrence is pending at a time.
- A pending occurrence is replaced by a newer generation or cancelled when the alerts end or change.
- A valid announcement that was claimed but never actually aired, because its deck failed before the first real buffer,
  is retried. Delivery requires authoritative first-real-buffer playback evidence, and an engine restart does not
  repeat a generation that has already aired.
- A pending, unclaimed occurrence is carried across a normal hour rollover through `_forced_next_items`, ahead of other
  forced items. The next hour's approved log is not modified.
- Playback is authorized only while the current source snapshots still produce the generation's content fingerprint.
  A cancellation, update or expiry therefore takes effect immediately, including during publication.

### CAP/IPAWS ingestion reliability

- Only Actual messages have authority. A Test, Exercise, System or Draft message never airs and never cancels or
  supersedes anything.
- An Actual Cancel retires what it references and an Actual Update supersedes what it references, including chains,
  in any feed order. An info-less Actual Cancel, which CAP permits, is parsed from its root fields and keeps its
  authority.
- Mandatory CAP 1.2 root and `<info>` fields are validated, with case-sensitive enumerations, before a message can be
  authoritative.
- A reference names a message by its complete identity: sender, identifier and sent time. Sender and identifier match
  exactly, and the sent time is compared as the instant it denotes. An alert from another sender that happens to share an
  identifier, or the same sender's alert at another time, is never retired by mistake. A malformed reference rejects
  the whole message.
- A partial retrieval, an unparseable message or a malformed qualifying message keeps the previous complete snapshot.
  It is never committed as a partial active set, and its known expiration deadlines are still enforced.
- Feed entries that lack an event or state classification are retrieved, within a bound, while an Actual alert of
  interest is held, because an info-less Cancel can look like that.
- Entries past their authoritative end are dropped even while an upstream feed is unavailable, and an entry with no
  authoritative end is conservatively excluded.

## What remains unchanged

- Program audio, scheduling, approved-log construction, live fill, Hour Refill (Roadmap 2.27), Active Messages and
  OGRemote.
- The Weather Alert Beep, forecast and current-conditions generation, and the polling schedules. Both pollers are
  scheduled one-shot processes and load the new source at their next invocation; there is no unit or timer change.
- Calibrated FLAC speech from r0134.

## Known operational limitations

- The first complete coordinator pass records the current alerts as a silent baseline. Alerts already in effect when
  r0137 first runs are not announced until the effective content changes.
- Upstream polling adds normal detection latency of up to one 5-minute poll interval.
- Retrieval of unclassified IPAWS entries is limited to 25 candidates per cycle. Above that, while an alert is held,
  the snapshot stays at its last complete state and a warning is logged. The live feed's typical count has not been
  measured from this host.
- An Actual Cancel that the feed classifies with a different event or state than the alert it cancels is not fetched.
  The alert then ends at its own expiration, unless the feed represents the cancellation otherwise.
- A persistently malformed upstream message can delay snapshot replacement until it is corrected or leaves the feed.
- A rare engine restart can lose a pending announcement that had been carried from the previous hour's log. The next
  coordinator pass re-queues a still-valid generation that has not aired.
- Generation attribution assumes ordinary forward-moving host-clock behavior; a backward clock step during an alert
  could misattribute a claim.
- While a source snapshot is missing or unreadable, a pending announcement is refused because it cannot be verified,
  and it is re-queued once the source is readable again.

## Deployment declaration

There are no migrations, migration companion, packages, Python requirements, collectstatic, nginx, systemd or
protected-runtime changes. `protected_runtime` is `null`.

Required restarts, in canonical order: `isadoraair-gunicorn`, then `isadoraair-engine`, then `isadoraair-monitoring`.
Gunicorn and the engine load the changed playout, state and publication code. Monitoring restarts because its Weather
probe imports the changed Weather diagnostics at run time. Encoders, RBDS, Active Messages, spoken rendering and other
services are not restarted.

An engine restart interrupts program audio and may end an active Remote DJ session. Publication does not authorize
installation at KOGR or WRJE; each station needs a separate preflight, installation authorization and production
acceptance. See `r0137_installation.md`.
