# r0138: Console and Remote DJ log display

r0138 improves the shared Coming Up table used by the full Console and Remote DJ without changing playout,
scheduling, queue advancement or playback authority. It adds the existing track intro marker to the display and a
station-wide, default-Off option to retain the current hour's aired items above the authoritative upcoming queue.

## Intro column

The Coming Up table now includes an **Intro** column in both Console and Remote DJ views. It displays the Track's
existing `intro_until_seconds` value as `M:SS`:

- an unset value is blank;
- an explicit zero is `0:00`;
- other values are rounded and formatted by the existing duration formatter.

The engine includes this already-loaded value in queue-status serialization without another database query. r0138
does not change cue-point storage, queue ETAs, duration calculation, Voice Track behavior or the interpretation of an
intro marker. The engine must restart before its status output includes the new field.

## Show played items

Django Admin → UI Theme → Console / Remote DJ — Log Display now has **Show played items**. The setting is
`UITheme.show_played_items`; it defaults to **Off** and takes effect when the page is reloaded.

With the setting Off, the Coming Up table keeps the r0137 upcoming-queue presentation. With it On:

- items with authoritative `played_at` evidence remain above the upcoming queue and keep their category hue under
  darker shading;
- the item the engine says is actually playing receives a thin white outline;
- a claimed, preloaded or paused item is shown as on deck rather than falsely identified as aired;
- upcoming items retain their ordinary category colors, order, ETAs and controls;
- only upcoming rows have drag, reorder and Next authority;
- the table remains scrollable and the operator's scroll position is preserved across ordinary refreshes.

The feature combines the existing authoritative engine queue with a read-only current-log history endpoint. History
never supplies upcoming ordering or a queue command target. Console and Remote DJ use the same rendering and safety
rules, subject to their existing authorization policies.

## Historical-fetch reliability

History is fetched on a log, queue or deck-state change and by a 30-second safety refresh, with a two-second minimum
attempt spacing. Each request has a six-second deadline. `AbortController` is used when supported, while an independent
timeout race guarantees that the in-flight slot is released even if a transport ignores abort. Per-request and
per-hour identities prevent a timed-out, late or previous-hour response from storing history or repainting the current
table.

At hour rollover the display adopts the new active log immediately. It intentionally does not preserve a previous-hour
outgoing track visually after that adoption. This presentation rule does not alter the engine's actual transition or
playback accounting.

## What remains unchanged

- The engine queue remains the sole authority for upcoming rows, queue order, ETAs and queue commands.
- Played and on-deck rows cannot be dragged, reordered or selected through Next.
- Playout scheduling, log construction, deck transitions, queue advancement and playback authority are unchanged.
- Voice Tracks, Web Requests, Hour Refill, Active Messages, Weather/AMBER, encoders and Remote DJ microphone authority
  are unchanged.
- There are no new packages, Python requirements, static assets, nginx changes, systemd units or protected-runtime
  changes. `protected_runtime` is `null` and collectstatic is not required.

## Inherited operational limitations

These pre-existing behaviors are not introduced or corrected by r0138:

- The server-side reorder API may accept played `LogItem` IDs from an otherwise authorized direct caller. The ordinary
  r0138 browser sends only current upcoming IDs.
- Default Remote DJ GroupAccess and the existing `schedule.edit` requirement may prevent a Remote DJ from successfully
  reordering even though the shared table displays its queue control.
- During a drag already in progress, an upcoming item can become claimed before the reorder reaches the server.
- Narrow mobile screens may require horizontal scrolling for the queue table.

## Engineering qualification

The accepted engineering review recorded 91 guarded server tests passing at the final engineering commit. The actual
rendered page passed 28 fixture-driven scenarios in Chromium and 28 in Firefox, including stalled transport, late
response, rollover and queue-control regressions. The old implementation failed the two intended negative controls.
Django checks and migration-drift checks were clean.

The committed Django Playwright module could not launch installed browsers from inside the guarded bubblewrap
environment. Those were executable-availability errors, not assertion failures; the host-driven browser harness is
separate and is not represented as execution of that committed module.

## Deployment declaration

Apply the additive migration `library.0101_uitheme_show_played_items`, then restart, in exact order:

1. `isadoraair-gunicorn`
2. `isadoraair-engine`

The migration adds one Boolean field with default `False`; no manual migration-authorization companion is required.
Gunicorn loads the new view, URL, template, admin and model code. The engine restart exposes the Intro marker in its
queue-status output and can interrupt program audio or end an active Remote DJ session, so installation requires an
operator-approved window.

Publication does not authorize installation at KOGR or WRJE. Each station requires separate preflight, installation
authorization and operational acceptance; see `r0138_installation.md`.
