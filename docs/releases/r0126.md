# r0126: Browser-initiated Library Reconciliation

r0126 delivers roadmap 3.11's minimal browser launcher for the existing read-only Library
Reconciliation scanner. An account with **Manage tracks** can select **Run Reconciliation** on
**Library → Reconciliation**. The request starts the existing `reconcile_library` management command
as a separate process and returns after a bounded two-second confirmation period. The browser then
follows the scanner's existing progress and report files.

The release does not add a scanner, scheduler, repair action, database model or background service.
It does not make reconciliation automatic. A scan remains a potentially expensive read-only review
and should be started outside busy hours.

## Launch and containment

The endpoint accepts no path, budget, command or other user-controlled launch argument. It always
executes the fixed command:

```text
/usr/bin/nice -n 19 /usr/bin/ionice -c 3 /usr/bin/gnutimeout --signal=KILL 2h \
    <current Python> <current manage.py> reconcile_library --no-color
```

* Gunicorn starts one detached process session and never performs the scan in the request.
* `gnutimeout` is the process-group leader. At two hours it sends `KILL` to the scanner and its
  ordinary FFmpeg/FFprobe descendants, including descendants that ignore `TERM`.
* The scanner's existing filesystem lock remains the authority for browser/CLI contention. A small
  launcher lock serializes only the start/confirmation window, preventing simultaneous browser
  requests from spawning duplicate contenders.
* The launcher supplies no shell, accepts no request arguments and closes inherited file descriptors.
* Scanner progress, last-attempt evidence and completed reports retain their existing schema and
  atomic publication behavior. An incomplete or killed scan never replaces the last completed report.

The two-hour limit does not promise to interrupt uninterruptible kernel I/O or an independently
detached descendant. Those exceptional operating-system conditions remain visible to operators and
are not a reason to add an unmanaged supervisor.

## Browser status behavior

The page disables duplicate submission while launch confirmation is in progress, pauses ordinary
polling during that request and resumes it afterward.

* A new progress record or new attempt identifies this launch; an older report is never presented as
  its result.
* If no new evidence appears within 30 seconds, the page says the start was not confirmed and keeps
  polling so a late result remains discoverable.
* A network failure or unstructured proxy response does not claim the scan failed to start. The page
  immediately refreshes authoritative reconciliation status. A newly running, completed, failed or
  interrupted scan wins over the uncertain POST outcome; the warning that whether the scan started is
  unknown appears only if the refresh finds no definitive new evidence.
* Generation guards stop delayed summary or findings responses from replacing a newer result.
* A browser retry is safe because the scanner and launcher locks still allow only one scan to run.

## Authorization and data guarantees

The page, summary, findings and launch endpoint require the existing `library.manage_tracks`
capability. The launch endpoint is POST-only and uses Django's normal CSRF protection. It returns no
new filesystem or process detail beyond the scanner status already available to an authorized Track
manager.

The launched command is the same existing scanner used by the CLI. It remains read-only with respect
to Track rows and media: it does not import, relink, delete, recategorize, approve, reanalyze or move
anything. Its only writes are its established lock, progress and report artifacts beneath the
configured reconciliation report directory.

## Deployment declaration

* **Migration:** none; no migration-authorization companion exists or is required.
* **Python requirements:** unchanged.
* **APT packages:** none added. The fixed launcher requires `/usr/bin/gnutimeout` from GNU coreutils;
  this is an existing station prerequisite, not a new package action. KOGR and WRJE have reported GNU
  coreutils 9.7, but each installation preflight must verify the executable and version again.
* **Systemd:** no unit, timer, policy or protected-runtime change.
* **Static and nginx:** unchanged; no `collectstatic` action.
* **Restart:** `isadoraair-gunicorn` only, so its workers load the new endpoint, launcher and page.
* **Not restarted:** engine, encoders, Monitoring, RBDS, Active Messages, spoken-render worker and all
  other station services.
* **Signing:** `protected_runtime` is `null`; under the established release trust model this ordinary
  application release has no protected descriptor, attestation or offline signing step. Its identity
  is the unique Git commit that introduces `deploy/releases/r0126.json` on canonical fast-forward
  history.

Publication does not authorize installation at KOGR or WRJE. See
[r0126_installation.md](r0126_installation.md).

## Not in this release

* no reconciliation schedule, service, timer or automatic scan;
* no database or media repair, import, deletion, relink or category change;
* no Monitoring integration;
* no engine, encoder, scheduler or playout change;
* no code from the abandoned `feature/3.11-browser-reconciliation` design;
* no Hour Refill or native Active Messages activation.
