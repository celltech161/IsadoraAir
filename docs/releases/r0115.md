## Release notes

### New

- **Operator board** — `/iportal/messages/board/`, for
  `active_message.control` only (Station Administrator by default;
  staff/superuser through the existing compatibility bypass). Every other
  account gets 403 on every board URL; GroupAccess still gates `/iportal/`.
  The iPortal hub keeps its one Active Messages entry and lists "My messages ·
  Operator board" under it for control users; producers keep My Messages
  (`/iportal/messages/`).
- **Compact, mobile-first layout** — a one-line status strip (active urgent /
  public-address counts, drafts to review, the current or last airing, the
  native-airing gate, an advisory over-limit alert, Replay now), filters
  (Current, Active, Review, History) with search, and two-line rows on a
  phone (one line of columns from 900 px) that expand in place: browser-only
  audio preview, facts, one primary action, expiry editor, recent events.
  Message and airing pages give full history; "All airings" lists every
  airing.
- **Operator lifecycle** on one exact message UUID through the existing
  services: Publish / Publish replacement (`activate_message` with the
  reviewed revision — audio saved after the review is never published
  unreviewed), Decline a draft and Clear an active message (confirmation page
  naming message and producer; `clear_message` with the expected state),
  expiry set / change / remove in station time (`set_message_expiry` with the
  expiry as shown; DST-skipped or repeated local times refused). A stale page
  changes nothing.
- **Accurate live ON AIR** — "on air" means only the STARTED airing and
  exactly the messages frozen in its composition (never the current active
  set); ACCEPTED and CLAIMED are labelled as such. A bounded 20-second refresh
  (at most 90 times) updates every ON AIR presentation; a response counts only
  while its request is the newest one sent, so a failed or late refresh can
  never restore obsolete ON AIR, and the page says "on-air indications may be
  out of date" until a newer refresh succeeds. Rows, focus and typed input are
  never disturbed.
- **Replay Now** (`request_manual_replay_outcome`, created / repeated /
  coalesced decided under the service's lock) is wired but **unavailable**:
  with the gate closed the button is disabled and the server refuses before
  the service, so no dormant airing is created.
- **Indexed, paginated execution history** — newest-first, keyset-paginated
  airing lists; message membership through a GIN index on the frozen
  composition snapshot; the status refresh does constant database work.

### Feature gates and defaults

- `NATIVE_AIRING_AVAILABLE` stays `False`; no active-message worker or unit.
- No new capability, role, setting, seed or static asset.
- OGRemote, Weather/AMBER, the engine, encoders, playout and the spoken
  pipeline are untouched.

## Migration

From an r0114 schema the target plan (the real `updatecenter_probe`
classifier over the exact on-disk migration; atomic) is one migration:

| # | Migration | SHA-256 | Operations | Classification |
| --- | --- | --- | --- | --- |
| 1 | `active_messages.0005_execution_history_indexes` | `2faa6b4aac94f7aaaa2dfede9c64cb1987a8153d9b737275c3e2ed8219d7af8e` | 0 AddIndex `active_execution_recent` — B-tree `(created_at, id)` on `active_messages_activebroadcastexecution`; 1 AddIndex `active_execution_members` — GIN `(composition_snapshot jsonb_path_ops)` | **manual ×2** ("operation is outside the Phase B v1 automatic allowlist") |

`migration_compatibility` is `additive`: no field, constraint or data
change; nothing is dropped or rewritten. The SQL is two plain
`CREATE INDEX` statements in one transaction. They are deliberately not
`CONCURRENTLY` (a non-atomic migration is manual for a worse reason: it can
partially commit). While they build, PostgreSQL holds a SHARE lock on the
execution table: reads continue, **writes to that table wait**. With native
airing closed nothing creates executions on a station (no worker, no unit,
Replay Now refused), so the table is expected to be empty or tiny and the
build instantaneous — **this expectation must be verified by the read-only
preflight below before the update is started.**

### Trusted migration authorization

The **two** manual operations — `active_messages.0005` #0 and #1, both
`AddIndex` — are covered by the trusted companion
`deploy/migration_authorizations/r0115.json`, introduced by its own
single-parent, metadata-only commit after the release commit. It binds
`release_id`, the release commit (`target_commit`), the SHA-256 of this
manifest's committed bytes and the migration file's exact SHA-256
(docs/UPDATE_CENTER.md, "Trusted companion migration authorization"). It
authorizes nothing of any earlier release. A station whose plan contains
exactly the covered operations (unioned with the companions of every other
release in its plan) needs no local approval; any other plan falls back to
exact station-local approval. The companion carries no signature: it
inherits the trust of the root-configured, fast-forward-only trusted
repository.

## Production database preflight (read-only; separately authorized)

Run on the target station before starting the update, as the application's
own database role, using `docs/releases/r0115_preflight.sql` (copy it from the
published r0115 commit — the station does not have it yet):

```
cd /opt/isadoraair
sudo -u <User= of the installed isadoraair-gunicorn unit> \
    venv/bin/python manage.py dbshell -- -X -v ON_ERROR_STOP=1 -f /path/to/r0115_preflight.sql
```

It runs in one `READ ONLY` transaction with a 10 s statement timeout and a
2 s lock timeout, and is rolled back. It writes nothing and kills nothing.
Each station (KOGR, WRJE, …) is checked on its own: their releases and data
differ.

**Proceed only if all of these hold; otherwise stop and reassess** (never
kill sessions or run the migration by hand to get past a finding):

| Check | Proceed when |
| --- | --- |
| 2. migration state | `0001`…`0004` applied, `0005_execution_history_indexes` **absent** (on a station older than r0113, `0003`/`0004` may be absent too — then they are in the plan and the station's whole plan must be reviewed) |
| 3. rows and size | exact rows ≤ 10 000 and total size ≤ 100 MB (expected: 0 rows — with the gate closed nothing creates executions; any rows deserve an explanation first) |
| 4. indexes | the existing indexes are valid and ready; neither `active_execution_recent` nor `active_execution_members` exists |
| 5. open transactions | no transaction older than 5 minutes (a long transaction delays the build's lock and every write queued behind it) |
| 6. table locks | no other session holds or awaits a lock on the execution table |
| 7. lock waits | no session waiting on a lock |

Also confirm the station's Update Center plan shows exactly the expected
migrations for its own installed release, the companion accepted and the
restart set below.

## What the update does

Planned by Update Center from r0114 (other stations: "Stations further
behind"):

| Step | Action |
| --- | --- |
| 1 | No protected-runtime handoff — generation 14 remains active |
| 2 | Stage the exact r0115 release target |
| 3 | Target migration probe; validate the r0115 companion (covers both manual operations) |
| 4 | Database checkpoint (`pg_dump`) |
| 5 | Apply `active_messages.0005` as one guarded atomic migration |
| 6 | Re-probe: schema clean |
| 7 | Checkout fast-forward r0114 (`9da1b4f`) → r0115 |
| 8 | No collectstatic (no static file changed), no unit install, no `daemon-reload` |
| 9 | Restart `isadoraair-gunicorn` |
| 10 | Postflight: exact checkout, clean schema, Gunicorn health |

**Restart and why:** Gunicorn serves every changed surface (the board's
views, URLs and templates, the recorder hub, `active_messages.services`).

**Not restarted, deliberately:** `isadoraair-engine` imports
`active_messages` only through `active_messages.playout`, which uses none of
the changed service functions (`activate_message`, `set_message_expiry`,
Replay Now); the model change is index metadata only, so the running r0114
engine code is fully compatible with the new indexes and nothing on air is
interrupted. The spoken render worker, `isadoraair-render`,
`isadoraair-validation`, `isadoraair-monitoring`, encoders, RBDS,
OGRemote and Weather/AMBER units run no changed code.

## Forward-only release and recovery

r0115 adds indexes only: r0114 code runs correctly against them, so a station
whose update stops after the migration keeps working on r0114 source (the
intended recoverable state). Update Center still promises **no automatic
rollback** (docs/UPDATE_CENTER.md, "Failure, retry, and rollback"):

| Failure point | State and supported handling |
| --- | --- |
| Before migration (steps 1–4) | Production unchanged. Retry. |
| During migration (step 5) | One guarded atomic migration with a root-recorded receipt: it either committed both indexes or neither. A lock wait simply delays it; an ambiguous interruption cannot auto-resume — manual intervention with evidence. Never kill sessions to clear locks. |
| After migration, before source advancement | Indexes present, r0114 source running — works normally. Retry or fix forward. |
| After source advancement / during the restart | `failed` / `manual_intervention_required` with evidence; fix forward. |
| After postflight | Installed. Fix forward with a corrected release. |
| Full pre-upgrade restoration | Only as disaster recovery restoring code and database together from the step-4 checkpoint through the approved procedure, with Recovery Assurance afterwards — never a code-only revert, never a hand-run `DROP INDEX`. |

   Gunicorn only, plus r0114's collectstatic from r0113), every manual

   unit/package/nginx step, and no protected-runtime step unless the station
   is at r0111 or older.
3. The read-only database preflight passed on **this** station.
4. Protected runtime healthy: active generation 14, no activation in
   progress; root execution armed.
5. A fresh, restorable pre-upgrade backup with a passing remote round-trip
   and Recovery Assurance `ok`; headroom for the `pg_dump` checkpoint.
6. Core services healthy; a quiet window (the update restarts Gunicorn).

## Post-install acceptance checklist (not executed during packaging)

Each step passes only as stated; any failure stops acceptance.

1. **Identity:** job succeeded; installed release r0115; HEAD is the r0115
   release commit, clean; only `isadoraair-gunicorn` restarted (engine,
   encoders, spoken worker, render, validation, monitoring, RBDS
   `ActiveEnterTimestamp` unchanged); generation 14 still active.
2. **Migration:** `showmigrations active_messages` shows `0005` applied;
   nothing pending anywhere.
3. **Indexes:** `active_execution_recent` (btree `created_at, id`) and
   `active_execution_members` (gin `composition_snapshot jsonb_path_ops`)
   exist, `indisvalid` and `indisready` true (preflight step 4 shows them).
4. **No pending migrations** (`manage.py migrate --check` exits 0).
5. **Web:** Gunicorn `/healthz/` `ok`; no new errors in its journal.
6. **Permissions:** a Station Administrator opens `/iportal/messages/board/`
   (200); a producer-only account and a non-producer get 403; the hub shows
   "Operator board" only to control.
7. **Presentation:** the board is compact on a phone (status strip, then the
   list; no sideways scrolling) and gains columns on a desktop.
8. **Status refresh:** the airing chip reads "No airings yet" (or the last
   airing) and native airing "closed"; leave the board open past a refresh —
   nothing jumps or resets. Optional: take the network away (airplane mode)
   for one refresh — "on-air indications may be out of date" appears and
   clears after the next successful refresh.
9. **Preview:** expanding a draft with audio plays it in the browser only;
   nothing reaches the station output.
10. **Native airing disabled:** "Replay now" is disabled and names why;
    `NATIVE_AIRING_AVAILABLE` is `False` in the installed source.
11. **OGRemote authoritative:** legacy urgent/PA processing unchanged; do not
    publish a live message to prove it.
12. **Broadcast uninterrupted:** the engine kept playing throughout (no
    restart, no gap); encoders, stream, RBDS and monitoring green.

Then run the existing post-release backup, remote round-trip and Recovery
Assurance.

## Known limitations and deferred work (D3E, nonblocking)

- The status refresh stops after about 30 minutes (90 × 20 s) and then says
  so; long-session behaviour should improve.
- "Airings with this message" work grows with that one message's own airings;
  exceptionally long-lived messages deserve better history scaling.
- Message History uses page numbers (count + sort on `terminal_at`), and
  detailed event-history navigation is basic.
- Monitoring, retention, failure recovery and active-message worker packaging
  remain D3E. A registered `updatecenter_migration_preflight` check for
  `active_messages.0005` (automating the read-only preflight above) is a
  candidate for that work.
- Browser behaviour was verified in headless Chromium only.

## Evidence required before declaring production acceptance

The completed preflight, identity, migration, index, permission and broadcast
checks above; the post-release backup, round-trip and Recovery Assurance
results; and the Update Center job evidence. Engineering acceptance is not
production acceptance.
