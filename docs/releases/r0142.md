# r0142: Past Overrides station-timezone HTTP 500 correction

r0142 is a corrective release for one defect in r0141. It changes one production function,
`_station_local_today()` in `library/views.py`, and adds regression tests. Restart **Gunicorn only**.

## Incident

r0141 introduced the **Past Overrides** list in Schedule → Date Override. The Schedule page loaded normally, but
selecting **Past Overrides** showed:

- `Past overrides could not be loaded.`
- `Request failed (500)`

It was observed during production acceptance after the r0141 installation on November 16, 2026. The station's web
access log recorded every `GET /api/schedule/past-overrides/` request answering HTTP 500. Every other r0141
acceptance check passed.

## Root cause

`_station_local_today()` passed the value returned by `get_station_timezone()` directly to Django's
`timezone.localtime()`. `get_station_timezone()` returns the configured station timezone **name** — a string such as
`"America/Chicago"`, read from Station Time (or `settings.TIME_ZONE` when that cannot be read). Django requires a
`tzinfo` object and raised:

`TypeError: tzinfo argument must be None or of a tzinfo subclass, not type 'str'`

The endpoint calculates the station date before reading any request parameter, so **every** request returned HTTP
500, including requests for an empty profile.

## Correction

`_station_local_today()` now converts the configured station timezone name with Python's standard-library
`ZoneInfo` before calculating the station-local date. An invalid or unavailable timezone configuration keeps the
established fallback to Django's default timezone (`settings.TIME_ZONE`), the same policy the request middleware
already applies, so a bad setting never takes the page down.

The calculation remains independent of the browser's timezone and of the request's activated timezone: Past
Overrides still lists explicit date overrides dated **before today in the configured station timezone**.

`get_station_timezone()`, its cache, the station-time middleware and the Station Time setting are unchanged.

## Testing

- **Why the r0141 tests missed it.** They either bypassed the station-date helper (most API tests patched
  `_station_local_today()` itself) or substituted a timezone object for the actual string return value (the two
  timezone tests patched `get_station_timezone()` to return `ZoneInfo(...)`).
- **Negative control on r0141.** A new module that follows the real production path — the station timezone stored as
  a string in Station Time, the real getter and helper, the authenticated test client, PostgreSQL — fails on r0141
  with 32 errors, every one the `TypeError` above. With the two corrected timezone tests, the r0141 result is 34
  errors, all the same `TypeError`.
- **Corrected result.** The new module and the existing Past Overrides tests pass: **32 of 32**. The new module
  covers: no historical overrides; past overrides with transitions at minutes other than `:00`; today's and future
  overrides excluded; station-local midnight against **UTC boundaries** for a station behind UTC and one ahead of
  it; **DST** spring-forward and fall-back, including the **repeated hour**; Rotation and Playlist name filtering;
  **profile isolation** across multiple Schedule Profiles; whole-date **pagination**; invalid query parameters and
  limit clamping; and the fallback for an unknown timezone name or an unreadable Station Time setting. The two
  existing timezone tests now patch the getter with its real string return type.
- **Browser.** The Past Overrides browser harness (simulated API, host Chromium) passes **52 of 52** checks, including
  new ones for an HTTP 500, an empty result, recovery after a failure and a failed **Load older dates**.
- **Related suites.** Station-timezone and middleware tests 50 of 50; the r0141 release contract 28 of 28.
- The Schedule module set is **not clean**: 264 tests with 2 failures and 20 errors, all in the Schedule browser test
  class `test_schedule_ui_async_3_1d`. They are **identical to the r0141 baseline** (Playwright browsers cannot
  launch inside the guarded validation sandbox) and are neither introduced nor corrected by r0142.

## Unchanged behavior

r0142 does not alter:

- Past Overrides listing, filtering, pagination or removal semantics;
- Schedule Profiles;
- Rotations or Playlists;
- existing schedule overrides;
- generated or approved logs;
- Console NEXT or Swap;
- the playback engine, decks or queue;
- Web Requests;
- Hour Refill;
- Remote DJ;
- Weather/AMBER alerts;
- Active Messages;
- station settings or stored content.

## Operational impact

There is no migration: `migrations_required` is empty and `migration_compatibility` is `null`. There are no new
packages, Python requirements, static assets, collectstatic, nginx changes, systemd units, manual bootstrap or
protected-runtime changes: `protected_runtime` is `null`. Restart exactly:

1. `isadoraair-gunicorn`

Only Gunicorn loads `library.views`; no other long-running service reaches the changed code. Under a direct
r0141 → r0142 update **the audio engine and encoders remain running** and program audio is not interrupted. A station
on an earlier release still receives every intervening migration and restart in its cumulative plan.

Publication does not authorize installation: each station requires separate preflight, installation authorization
and operational acceptance; see `r0142_installation.md`.
