# r0140: Remote DJ automatic reconnect and navigation protection

r0140 delivers roadmap 2.17 Package B for Remote DJ, on the full Console and the dedicated `/remote-dj/` page:

1. an optional **automatic fresh-session reconnect**, controlled by a new station switch that is **Off by default**;
2. an always-on **leave-page warning** while the page owns a Remote DJ connection;
3. corrected **microphone lifecycle** cleanup in the browser.

The release adds one additive migration (`library.0103_remotedjconfig_auto_reconnect_enabled`) and requires restarting
`isadoraair-gunicorn`, then `isadoraair-engine`. **The engine restart interrupts program audio and ends any live Remote
DJ session.** Publication does not authorize installation at KOGR or WRJE; see `r0140_installation.md`.

## Automatic fresh-session reconnect

### Station switch (Off by default)

Django Admin → **Remote DJ Configuration** → **Reconnect / recovery** has a new field below the existing grace setting:
**Enable automatic Remote DJ reconnect** (`RemoteDJConfig.auto_reconnect_enabled`). It is a Boolean, default False,
so every station keeps today's behavior after installation: a lost session stays disconnected until the DJ presses
Connect. Changes are recorded by the existing configuration audit (apply mode
`next_remote_dj_reconnect_decision`, no restart). Remote DJ's own master switch (`enabled`) must also be on.

When disabled, the switch prevents subsequent automatic reconnect attempts at their next policy decision. It does not
necessarily cancel a connection attempt already negotiating: an attempt that already received a `retry` decision ends
normally, by establishment, failure or its establishment bound.

### Same-session recovery versus a new session

The existing temporary **same-session recovery** (the engine's muted "Reconnecting" grace, `reconnect_grace_seconds`,
3–30 s) is unchanged and always comes first. It keeps the same session when the transport recovers in time.
Automatic reconnect is a different mechanism: it is considered only after the old session has **definitively ended**,
and it starts a completely **new session**. It is not ICE restart and not same-session migration.

### What qualifies

A sequence starts only when an **established** session (its ICE reached connected) ends with a terminal signal this
page did not cause: the server closing the signaling socket, or ICE `failed` / `closed`. It never starts after the
DJ's Disconnect, Cancel, leaving the page, a Kick message or a failed first Connect.

Before every attempt the browser asks `GET /api/remote-dj/reconnect-policy/` (under the existing `/api/remote-dj/`
group access). The engine now records why each session ended (`end_reason`) and whether an Emergency Mute was latched
at that moment, and publishes the r0132 slot admission state (`remote_dj_slot`). The server answers:

- `stop` after an administrator **Kick**, an **authorization revocation**, an **engine shutdown**, an unclassified
  end, an **Emergency Mute latched** when the session ended, a **quarantined** slot, another active session, an engine
  that no longer knows the lost attempt (for example after an engine restart), a refused token, or when the switch,
  Remote DJ, the `remote_dj.connect` capability or the schedule window does not permit it;
- `wait` while the lost session is still finalizing or its bounded native cleanup is running (`cleaning`), or engine
  status is unavailable; this spends no attempt;
- `retry` otherwise: start one new attempt.

The endpoint authorizes nothing by itself. Every attempt still needs a fresh token and normal admission, and anything
other than a readable `retry` is treated as not authorized.

### Bounded, visible and cancellable

| Bound | Value |
|---|---|
| Attempts per qualifying loss | 3 |
| Backoff before attempts 1 / 2 / 3 | 1 s / 2 s / 4 s |
| Establishment bound per attempt | 30 s, never beyond the sequence deadline |
| Whole-sequence deadline | 150 s (authoritative; measured on both the monotonic and wall clocks) |
| Fresh budget | only after a replacement stayed established ≥ 60 s |
| Sequences per page per hour | 6 |

While a sequence runs, the Connect button shows `Reconnecting…`, `Waiting for connection…` or `Retrying N of 3` with
a **Cancel reconnect** action, and the Remote Mic gate is unavailable. When a sequence stops the button briefly says
why (`Reconnect failed`, `Reconnect cancelled`, `Disconnected by the station`, `Muted by the station`, `Reconnect not
permitted`, …). A manual Connect is always available afterwards, subject to normal admission.

### Fresh resources and Remote Mic Off

Each attempt is a complete new session: a new token and attempt identity, a new WebSocket, a new
`RTCPeerConnection`, a new microphone stream and a new AudioContext. An old control key is never reused. A replacement
counts as established only when its ICE is connected **and** a trusted engine snapshot names this page's attempt as
the owner.

**The Remote Mic is Off when every replacement session is established** (the engine opens every session muted), and
gate commands addressed to the old session are refused by the engine's exact attempt/session binding.

## Navigation protection

- **Application-controlled confirmation.** While the page owns an active or establishing connection, or a pending
  automatic reconnect, same-tab links and form submissions open a dialog ("You have a live Remote DJ audio session in
  progress…") with **Stay on this page** (default, also Esc) and **Leave and disconnect**. Staying changes nothing;
  leaving ends any reconnect sequence, disconnects and then navigates.
- **Native browser warning.** Back, Reload, closing the tab or window, typed URLs and script navigation get the
  browser's own leave-page prompt from a `beforeunload` handler installed only while the page owns a connection.
- **Browser limitations.** Browsers show their own generic text in that native prompt, not ours, and require a prior
  user interaction on the page. Some mobile exits (app switch, OS tab discard) show nothing, and `pagehide` is used
  only as best-effort release; it is never relied on as cleanup.
- **Leaving still ends the connection.** Navigating away, reloading or closing the page still destroys the page-owned
  Remote DJ connection. The warning prevents accidents; it does not keep audio alive. A page that only observes
  another browser's session never prompts.
- **Persistent ownership is not included.** Keeping one Remote DJ connection alive across page navigation (a
  dedicated window or shared owner) belongs to Package C.

## Microphone lifecycle

- **Pre-existing cleanup defect corrected.** Before r0140 a Disconnect closed the AudioContext but did not stop the
  `getUserMedia` tracks, so the microphone capture (and the browser's microphone indicator) stayed alive. Every local
  release now goes through one function that closes the peer connection, WebSocket and AudioContext exactly once and
  **stops the microphone source tracks**.
- **Web Audio destination tracks.** The output (`MediaStreamDestination`) tracks are now stopped explicitly; Chromium's
  `AudioContext.close()` does not end them.
- **Failed WebRTC setup.** A rejection while an offer is applied (remote description, microphone, AudioContext / Web
  Audio graph, missing transceivers, `replaceTrack`, `createAnswer`, `setLocalDescription`, sending the answer) is
  handled, never left unhandled. A manual Connect shows `Setup failed` and never starts a reconnect; an automatic
  replacement spends one attempt of the same sequence.
- **Attempt-bound cleanup and deadline enforcement.** Every timer, policy response, token response, socket event,
  offer step and microphone result is bound to its attempt and sequence. A late failure of a superseded attempt
  releases only what that attempt created, never a successor's resources. The 150 s deadline is re-checked after
  every policy answer, before a token is requested, after the token and microphone arrive, before the answer is sent
  and before a replacement is adopted.

## Unchanged behavior

- Exact-session PTT and administrator controls (Mute, Kick, Emergency Mute) and their attempt/session binding.
- Existing **session-scoped Emergency Mute** semantics: a latch is not persisted across sessions. A latch present when
  the session ended stops automatic reconnect; a new session started manually begins unlatched, as before.
- r0132 bounded native teardown and quarantine; a quarantined slot still requires an engine restart.
- Manual/Auto ownership and mix-minus.
- Remote DJ quality thresholds and the Opus monitor settings (10 ms monitor return).
- Ordinary scheduling, log building, program playout, Hour Refill, Weather/AMBER, Active Messages and encoders.
- Same-session ICE restart, TURN and persistent cross-page WebRTC ownership are **not** included.

## Known limitations

- **Simulation-based browser testing.** The browser behavior was qualified with a host Chromium harness against the
  real rendered Console and `/remote-dj/` pages, with WebSocket, `RTCPeerConnection`, `getUserMedia`, AudioContext and
  every network request replaced by deterministic fakes and a fake clock. No real WebRTC session with a running
  engine, and no mobile browser, was exercised during engineering. Real-engine and mobile acceptance remain field
  work.
- **Exception-injection coverage.** Rejections are injected at `replaceTrack`, `createAnswer`,
  `setLocalDescription`, `setRemoteDescription` and missing transceivers. A rejected `getUserMedia`, a failing
  AudioContext / Web Audio construction and a failing answer send are routed through the same handler but are not
  individually injected. Codex recommended this additional coverage as nonblocking; it is not part of r0140.
- A page reload or navigation always ends the session; the native prompt's wording and presence are
  browser-controlled.
- After an engine restart the engine has no record of the lost attempt, so no automatic reconnect follows (by design:
  ambiguous ⇒ no retry).
- A forward wall-clock correction during a sequence can end it early (fail-closed).
- A `retry` decision is not bound to the engine instance that later admits the replacement (an engine-instance
  time-of-check/time-of-use window). Codex accepted this as nonblocking under the existing fresh-token, admission and
  muted-start safeguards; r0140 does not change the protocol to remove it.

## Engineering qualification

Codex completed an independent adversarial review of `3321ad4` (four findings) and a focused re-review of the
corrected candidate `0a75798`, accepting it for release engineering with no remaining release-blocking defect. The
accepted engineering evidence records 474 of 474 focused Remote DJ tests passing; 452 of 452 Chromium harness checks
(226 per page); and deterministic negative controls that reproduce the original defects on `3321ad4` (274 passed,
178 failed) and on r0139 (microphone capture left alive after Disconnect).

The historical full `library` + `authz` run is **not clean**: it reported 451 failure/error identifiers, identical
on the accepted candidate and the reviewed candidate and with none new compared with r0139. They are environmental
(Playwright browsers cannot launch inside the guarded sandbox, `MediaRejected` media fixtures, read-only media
paths) and inherited; r0140 neither introduces nor corrects them.

## Deployment declaration

Apply the additive migration `library.0103_remotedjconfig_auto_reconnect_enabled` (one non-null `AddField` of a
Boolean with literal default False; existing `RemoteDJConfig` rows receive False), then restart exactly, in this
order:

1. `isadoraair-gunicorn`
2. `isadoraair-engine`

Gunicorn serves the new policy endpoint, Admin field and page code; the engine publishes the session end reasons and
slot state. No other long-running service loads the changed code. No manual migration-authorization companion is
required. There are no new packages, Python requirements, static assets, collectstatic, nginx changes, systemd units
or protected-runtime changes: `protected_runtime` is `null`.

**The engine restart interrupts program audio and ends any live Remote DJ session.** Installing r0140 does not
enable automatic reconnect. Publication does not authorize installation: each station requires separate preflight,
installation authorization and operational acceptance; see `r0140_installation.md`.
