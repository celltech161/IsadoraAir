# HE-AAC native dependency provenance

Runtime Foundation D makes this dependency reproducible from exact local
source archives without GitHub. `isadoraair/runtime_components.json` is the
single machine-readable authority; `deploy/build_fdkaac.sh` consumes it and
`deploy/check_he_aac.sh` is the shared linkage/capability validator. Foundation
D does not replace the installed production binaries or complete the entire DR
payload/provisioner roadmap.

## Why Ubuntu's packaged fdkaac isn't sufficient

Explained in the code itself
(`encoders/services/encoder_manager.py`'s `_format_block`, right where
`FDKAAC_PATH` is used) — repeated here because it's the entire reason
this dependency exists outside apt at all:

- **Ubuntu's `fdkaac` package** (`fdkaac 1.0.0-1build1`, at
  `/usr/bin/fdkaac`) links against Ubuntu's `libfdk-aac2` package
  (`2.0.2-3~ubuntu5`), which ships with **SBR (spectral band
  replication) and Parametric Stereo stripped** — profile 5 (HE-AAC)
  and profile 29 (HE-AAC v2) both fail with "unsupported profile" —
  for legacy software-patent reasons around the Fraunhofer FDK AAC
  license terms and downstream distribution.
- **Liquidsoap's own `%fdkaac(...)` binding** isn't usable either: the
  Ubuntu `liquidsoap` package isn't built with the `fdkaac` OCaml
  binding (confirmed via `liquidsoap --list-plugins` showing no
  `liquidsoap_fdkaac`), so the format parses at Liquidsoap script
  check-time but throws "unsupported format" at runtime.
- **ffmpeg's native `aac` encoder** exists as a fallback but is LC-only
  and sounds materially worse at the low bitrates (24-96 kbps) this
  project actually streams at — not a serious substitute.

So production routes AAC through an absolute path,
`/usr/local/bin/fdkaac`, deliberately never looked up via `PATH` — a
custom build of the upstream `nu774/fdkaac` command-line frontend,
linked against a custom build of upstream `mstorsjo/fdk-aac` itself.

## What's actually installed (confirmed by direct inspection)

| `libfdk-aac` codec library | `/usr/local/lib/libfdk-aac.so.2.0.3` (symlinked as `.so.2` and `.so`) | `pkg-config` metadata at `/usr/local/lib/pkgconfig/fdk-aac.pc`: `Version: 2.0.3`. Also dated 2026-07-12 — same session as the frontend, consistent with both being built together. |

| Ubuntu's own copies (present, unused by IsadoraAir) | `/usr/bin/fdkaac` (pkg `fdkaac 1.0.0-1build1`), `/usr/lib/x86_64-linux-gnu/libfdk-aac.so.2.0.2` (pkg `libfdk-aac2 2.0.2-3~ubuntu5`) | `dpkg -S`/`dpkg -l` — genuinely apt-managed, just not what IsadoraAir actually uses. `PATH` order (`/usr/local/bin` before `/usr/bin`) plus `FDKAAC_PATH`'s absolute path both independently guarantee the custom build wins. |

The authoritative capability test is not the help listing. The shared
validator performs real profile **2 (AAC-LC), 5 (HE-AAC/SBR), and 29 (HE-AAC
v2/SBR+PS)** encodes and makes ffmpeg decode every result. This is necessary
because the Ubuntu frontend lists profiles that its stripped library rejects.

## Was exact historical build provenance recoverable?

**No, and this document says so plainly rather than guessing.**
Checked:

- No source tree for either `nu774/fdkaac` or `mstorsjo/fdk-aac` remains
  anywhere on the host (`/home/jreed`, `/usr/local/src`, `/opt`, `/tmp`
  all checked).
- No build script, `Dockerfile`, Makefile fragment, or written notes
  exist anywhere in the IsadoraAir repo referencing either upstream
  project by name.
- `~/.bash_history` contains exactly one fdk-aac-related line —
  `sudo apt install libfdk-aac2` (installing the *Ubuntu* package,
  presumably pulled in as a dependency of something else at some
  point) — and **no** `git clone`, `./configure`, `make`, or `make
  install` commands for either upstream project. Whatever shell session
  actually built these was either not run interactively with history
  enabled, predates the current history buffer, or was run by a
  different mechanism entirely (a one-off script, a different user, a
  now-gone terminal). This audit does not know which, and does not
  guess.

**This means bit-for-bit reproduction of the exact historical build is
not achievable from current evidence, and that should not be treated as
a requirement.** What the evidence *does* establish unambiguously is
**which upstream release versions are actually running in production
right now** (`fdkaac 1.0.7`, `fdk-aac 2.0.3`) — which is sufficient to
define a new, current, buildable, testable pinned target.

| fdkaac | 1.0.7 | `fdkaac-1.0.7.tar.gz` | 86,687 | `145d4684c9325a2bd650e46a04b03327abe780a7b59cce47e6de8af2064fb2c7` | `COPYING` |

The exact archive identity, not an upstream tag name recreated later, is the
rebuild input. Historical compiler byte identity and installed-binary hash
identity are deliberately not acceptance criteria. The contract is exact
source bytes, pinned versions, one build procedure, intended linkage, and real
codec capability.

## One acquisition/build path

GitHub-free local/DR mode is:

```bash
deploy/build_fdkaac.sh \
  --source-dir /path/to/native/fdkaac \
  --prefix /tmp/isadoraair-fdkaac-stage
```

It requires both exact archive filenames, checks SHA-256 and byte count before
extraction, and fails on missing or mismatched input. It never falls back to
the network. The archives are opened read-only and extracted into an automatic
`/var/tmp/isadoraair-fdkaac-build-*` workspace (or an explicitly supplied
`--build-dir`); only the extracted copies are changed by `autoreconf` and the
build. Automatic workspaces are removed on success or failure. A caller-owned
`--build-dir` is retained for inspection and must start empty.

Connected fresh installs may deliberately use:

```bash
deploy/build_fdkaac.sh --download-sources \
  --prefix /tmp/isadoraair-fdkaac-stage
```

This downloads the manifest URLs into the temporary workspace, verifies the
same identities, and then joins the identical extraction/build/install path.
There is no Git clone recipe and no second DR recipe.

`--prefix` is mandatory and must be absolute. `/usr/local` has a second guard,
`--allow-production-prefix`; nothing defaults there. A repeated staging build
uses a fresh workspace and safely replaces the files beneath the explicitly
selected staging prefix. The script does not run `ldconfig`.

## Build and validation authority

The declared Ubuntu 26.04 prerequisites are the `BUILD_HEAAC` group in
`deploy/packages-ubuntu-26.04.txt`: `build-essential` (through `CORE`),
`autoconf`, `automake`, `libtool`, and `pkg-config`. `tar`, `coreutils`,
`libc-bin`, and Python are baseline packages; `ffmpeg` is in
`AUDIO_GSTREAMER`. Optional network acquisition additionally declares `curl`
and `ca-certificates`. Local-source mode does not require Git or curl.

The build installs fdk-aac first. fdkaac configuration receives a closed
`PKG_CONFIG_LIBDIR`, plus include/library paths for that same prefix, preventing
an accidental build against Ubuntu's 2.0.2 development metadata. After every
build, the shared validator proves:

1. fdkaac reports version 1.0.7;
2. the selected prefix exposes fdk-aac 2.0.3 metadata and versioned library;
3. `readelf` declares `libfdk-aac.so.2` and `ldd`, under the selected staged
   library path, resolves the exact 2.0.3 file rather than `/usr/lib` 2.0.2;
4. profiles 2, 5, and 29 all encode a synthetic tone;
5. ffmpeg decodes all three outputs.

The same validator serves production, staged restore, installer, and future
Encoder/Aircheck preflight contexts:

```bash
deploy/check_he_aac.sh                         # canonical /usr/local
deploy/check_he_aac.sh --prefix /tmp/stage     # isolated prefix
deploy/check_he_aac.sh --fdkaac PATH --lib-dir PATH
deploy/check_he_aac.sh --fdkaac PATH --lib-dir PATH --runtime-only
```

`--runtime-only` serves Foundation E4's deliberately minimal canonical
publication, which excludes build-only pkg-config metadata. It still checks
the exact expected versioned library filename, fdkaac version, ELF dependency
and exact resolution, and all three encode/decode profiles. Ordinary staged
build validation remains the stricter pkg-config-aware default.

It exits nonzero on any version, linkage, capability, or decode failure. It
performs three real encodes and decodes (about 0.23 seconds on the audited
host), so it is appropriate after install, during a restore, and in the
existing operator-run deployment-baseline check. A future normal
Encoder/Aircheck preflight should cache installation validation rather than put
this probe on the real-time engine path or rerun it on every service start.
Foundation D does not change Encoder or Aircheck startup behavior.

## DR payload and license contract

The future private DR payload layout is:

```text
native/fdkaac/
  fdk-aac-2.0.3.tar.gz
  fdkaac-1.0.7.tar.gz
  SHA256SUMS
  provenance/
    fdk-aac-NOTICE
    fdkaac-COPYING
```

`SHA256SUMS` must be generated from and checked against the runtime manifest;
it is not an independent version authority. The exact archives already contain
fdk-aac's complete `NOTICE` and fdkaac's `COPYING`; the separately visible
copies make license/notice review possible without extracting source. In
particular, fdk-aac's notice requires its complete license text to accompany
redistribution and describes source-availability and patent-license terms.

`deploy/restore/50-native-deps.sh --source-dir ...` and
`FDKAAC_SOURCE_DIR=...` already hand such a directory to the authoritative
builder. If omitted, the current restore wrapper explicitly selects connected
acquisition and warns; there is no silent fallback after local mode is chosen.
The normal backup does not yet capture this private native payload, so the
overall disaster-recovery archive remains unfinished.

## Deliberate production publication and rollback

Foundation E4 supplies the reusable publication adapter; this checkpoint does
not execute it in production. Its unprivileged phase invokes Foundation D only
with `--source-dir` and a staging prefix. Its separately privileged phase
requires an explicit trusted administrative preparer UID, verifies that UID
and non-shared-writable ownership on the prepared handoff, copies the verified
runtime files into private same-filesystem staging, runs
the full validator there, snapshots and atomically replaces only the exact
versioned library and fdkaac executable, runs `ldconfig`, and performs
canonical runtime-only E2 validation. Failure restores the exact prior
present/absent file state, reruns `ldconfig`, and compares fdkaac E2 evidence.
Ubuntu's older 2.0.2 must never satisfy the intended-library resolution check.
The trusted preparer is a provisioning/admin identity, not a runtime service
account; the receipt's recorded UID is diagnostic and never an authority.
E4 assumes honest preparation by that trusted actor; it proves the manifest
source contract, handoff consistency, protected root-owned re-copy, hashes,
Foundation D functionality, and canonical E2 acceptance, but intentionally
does not cryptographically attest that a malicious preparer ran the audited
builder. A compromised IsadoraAir runtime identity must therefore never be
selected as the trusted preparer.
