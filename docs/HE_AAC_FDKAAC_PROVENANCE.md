# HE-AAC native dependency provenance

Roadmap item 1.2 Phase 2 — closes the *documentation/provenance* gap only.
**Nothing was built, installed, or modified to produce this document.**
The actual reproducible-build automation is Phase 3 work; this document
exists so Phase 3 has a clear, evidence-based pinned target instead of
starting from nothing.

## Why Ubuntu's packaged fdkaac isn't sufficient

Explained in the code itself
(`encoders/services/encoder_manager.py`'s `_format_block`, right where
`FDKAAC_PATH` is used) — repeated here because it's the entire reason
this dependency exists outside apt at all:

- **Ubuntu's `fdkaac` package** (`fdkaac 1.0.0-1build1`, at
  `/usr/bin/fdkaac`) links against Ubuntu's `libfdk-aac2` package
  (`2.0.2-3~ubuntu5`), which ships with **SBR (spectral band
  replication) and Parametric Stereo stripped** — profile 5 (HE-AAC)
  and profile 29 (HE-AAC v2) both fail with "unsupported profile" —
  for legacy software-patent reasons around the Fraunhofer FDK AAC
  license terms and downstream distribution.
- **Liquidsoap's own `%fdkaac(...)` binding** isn't usable either: the
  Ubuntu `liquidsoap` package isn't built with the `fdkaac` OCaml
  binding (confirmed via `liquidsoap --list-plugins` showing no
  `liquidsoap_fdkaac`), so the format parses at Liquidsoap script
  check-time but throws "unsupported format" at runtime.
- **ffmpeg's native `aac` encoder** exists as a fallback but is LC-only
  and sounds materially worse at the low bitrates (24-96 kbps) this
  project actually streams at — not a serious substitute.

So production routes AAC through an absolute path,
`/usr/local/bin/fdkaac`, deliberately never looked up via `PATH` — a
custom build of the upstream `nu774/fdkaac` command-line frontend,
linked against a custom build of upstream `mstorsjo/fdk-aac` itself.

## What's actually installed (confirmed by direct inspection)

| Item | Path | Evidence |
|---|---|---|
| `fdkaac` frontend | `/usr/local/bin/fdkaac` | `fdkaac --help` header: `fdkaac 1.0.7`. ELF 64-bit, dynamically linked, **not stripped** (retains debug info), dated 2026-07-12. |
| `libfdk-aac` codec library | `/usr/local/lib/libfdk-aac.so.2.0.3` (symlinked as `.so.2` and `.so`) | `pkg-config` metadata at `/usr/local/lib/pkgconfig/fdk-aac.pc`: `Version: 2.0.3`. Also dated 2026-07-12 — same session as the frontend, consistent with both being built together. |
| Build tooling used | GNU libtool | `/usr/local/lib/libfdk-aac.la`'s own header: `Generated by libtool (GNU libtool) 2.5.4 Debian-2.5.4-9` — confirms a standard autotools (`autogen.sh` / `configure` / `make` / `make install`) build, the normal process for both `mstorsjo/fdk-aac` and `nu774/fdkaac`, not a hand-rolled or nonstandard toolchain. |
| Ubuntu's own copies (present, unused by IsadoraAir) | `/usr/bin/fdkaac` (pkg `fdkaac 1.0.0-1build1`), `/usr/lib/x86_64-linux-gnu/libfdk-aac.so.2.0.2` (pkg `libfdk-aac2 2.0.2-3~ubuntu5`) | `dpkg -S`/`dpkg -l` — genuinely apt-managed, just not what IsadoraAir actually uses. `PATH` order (`/usr/local/bin` before `/usr/bin`) plus `FDKAAC_PATH`'s absolute path both independently guarantee the custom build wins. |

**Confirmed capability** (`fdkaac --help` on the installed
`/usr/local/bin/fdkaac`, `-p`/`--profile` option): profiles **2 (AAC
LC), 5 (HE-AAC/SBR), and 29 (HE-AAC v2/SBR+PS)** are all listed as
available — exactly the three tiers `encoder_manager.py`'s bitrate-based
profile selection needs, and exactly what Ubuntu's packaged build
cannot do. This was **not** verified by actually running an encode in
this pass (Phase 2 is documentation-only, not a build/test pass) — that
live verification belongs to Phase 3 (see "How Phase 3 should verify
success" below).

## Was exact historical build provenance recoverable?

**No, and this document says so plainly rather than guessing.**
Checked:

- No source tree for either `nu774/fdkaac` or `mstorsjo/fdk-aac` remains
  anywhere on the host (`/home/jreed`, `/usr/local/src`, `/opt`, `/tmp`
  all checked).
- No build script, `Dockerfile`, Makefile fragment, or written notes
  exist anywhere in the IsadoraAir repo referencing either upstream
  project by name.
- `~/.bash_history` contains exactly one fdk-aac-related line —
  `sudo apt install libfdk-aac2` (installing the *Ubuntu* package,
  presumably pulled in as a dependency of something else at some
  point) — and **no** `git clone`, `./configure`, `make`, or `make
  install` commands for either upstream project. Whatever shell session
  actually built these was either not run interactively with history
  enabled, predates the current history buffer, or was run by a
  different mechanism entirely (a one-off script, a different user, a
  now-gone terminal). This audit does not know which, and does not
  guess.

**This means bit-for-bit reproduction of the exact historical build is
not achievable from current evidence, and that should not be treated as
a requirement.** What the evidence *does* establish unambiguously is
**which upstream release versions are actually running in production
right now** (`fdkaac 1.0.7`, `fdk-aac 2.0.3`) — which is sufficient to
define a new, current, buildable, testable pinned target.

## Recommended Phase 3 pinned target

Build both from their upstream GitHub release tags matching the
versions actually confirmed running:

- **`mstorsjo/fdk-aac`**, tag `v2.0.3` — standard autotools build
  (`./autogen.sh && ./configure && make && sudo make install`), installs
  to `/usr/local/lib` + `/usr/local/include/fdk-aac` by default, matching
  what's already there.
- **`nu774/fdkaac`**, tag `v1.0.7` — same autotools pattern, depends on
  the `fdk-aac` install above (via `pkg-config`, confirmed present at
  `/usr/local/lib/pkgconfig/fdk-aac.pc`) being on `PKG_CONFIG_PATH` at
  build time.

Both are exact-version matches to what's already installed and proven
working in production — not a guess at "some recent version," an actual
confirmed-compatible pin.

**Required system build dependencies** (for Phase 3's own automation to
install first): `build-essential`, `autoconf`, `automake`, `libtool`,
`pkg-config` — the standard C build toolchain `README.md` already lists
for other native-wheel Python packages, likely already present as a
matter of that overlap but not yet confirmed specifically for this build.

## How Phase 3 should verify success

Not "does it compile" — **does it actually produce the exact codec
behavior IsadoraAir depends on**:

1. `fdkaac --help` output must list profiles 2, 5, and 29 as available
   (matches the check this document already ran against the current
   binary).
2. A real, controlled test encode at each of the three tiers
   `encoder_manager.py` actually selects by bitrate — AAC-LC (128+
   kbps), HE-AAC/SBR (80-96 kbps), HE-AACv2/SBR+PS (24-64 kbps) — from a
   short known-good WAV source, confirming each one **succeeds** (not
   "unsupported profile") and produces plausible output (non-trivial
   file size, decodes back cleanly with `ffprobe`/`ffplay`).
3. `ldd /usr/local/bin/fdkaac` resolves to the freshly-built
   `/usr/local/lib/libfdk-aac.so.2`, not Ubuntu's `libfdk-aac2` package
   copy — confirms the link path, not just that *a* working binary
   exists somewhere.
4. `encoders/services/preflight.py`'s existing fdkaac dependency check
   (already covered by `encoders/tests/test_preflight.py`) passes
   against the freshly-built binary with no code changes needed — the
   whole point of pinning to the versions already running is that
   nothing downstream should need to change.

None of the above was executed in this pass — Phase 2 is documentation
only, per its own explicit scope boundary.
